# 批量渲染实验：每帧消费 1/2/5/10/20 点的二维与三维对比

对应 [优化过程.md](../../docs/优化过程.md) 第 3.2 节「批量渲染实验」。该节提出了一个假设：长帧主要来自「每次地图更新的固定成本 F」，而非「单点处理成本 P」；若成立，把多个点合并进一次更新即可摊薄 F。本报告用统一条件的实测数据检验该假设。

## 实验条件

固定不变（除每帧点数外的全部条件）：

```text

订阅档位：全部接收
持续时间：约 60 秒
历史起点：0 个可视点（冷启动）
```

## 分析

### 1. 二维：批量同时恢复了吞吐和流畅度，支持「固定成本主导」

二维对 batch 的响应是**同向的双重改善**：

```text
batch 1 → 20
消费能力   414 → 1180 点   （2.85 倍）
rAF FPS    10.49 → 54.94  （5.24 倍）
LoAF 次数  413 → 110      （-73%）
pending    766 → 0
```

数据总量没有变化（仍是 20 点/秒），减少的只是**地图被触发的更新次数**。这正是优化过程.md 3.3 节【情况一】描述的特征：性能出现数量级改善，说明 `F >> P`。

还有一个关键旁证：二维第二阶段的**中位数反而下降**（126.3 ms → 83.1 ms）。如果单点处理成本 `P` 占主导，批量变大后单帧工作量增加，这个数字应当上升。它反而下降，说明二维的主要成本是「进入一次地图更新就要支付的固定开销」，批量把这份开销摊薄了。

### 2. 三维：批量提高了吞吐，却让 FPS 更低、长帧更严重

三维的响应方向与二维**相反**：

```text
batch 1 → 20
消费能力   342 → 1140 点   （3.33 倍，吞吐确实提高）
rAF FPS    9.07 → 7.47    （-17.6%，反而下降）
LoAF P95   249.5 → 739.2 ms（+196%，显著恶化）
LoAF 平均  166.2 → 304.9 ms
pending    818 → 0        （队列最终清空）
```

吞吐与流畅度出现**背离**：队列被清空了，但页面更卡。这对应 3.3 节【情况三】，并且直接印证了 3.4 节那句提醒——「LoAF 数量减少并不能单独证明性能改善」。三维 LoAF 次数从 343 降到 180（-47.5%），但单条长度几乎翻倍，用户体验反而更差。

另外，三维在 batch = 20 时 `pending` 归零、消费追平输入，但 FPS 仍只有 7.47、P95 长帧 739 ms。**「队列清空」不等于「页面流畅」**，这是本轮最需要强调的一点。

### 3. 三维的单帧 Cesium 成本随批量单调上升

三维全部长帧都归因到 Cesium 的 rAF 回调。把它按「累计耗时 ÷ 长帧数」换算成单帧成本：

| batch | 1 | 2 | 5 | 10 | 20 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单帧 Cesium 回调均值 | 41.0 ms | 52.2 ms | 85.7 ms | 124.3 ms | 134.6 ms |
| Cesium 累计占比 | 23.4% | 25.3% | 30.6% | 37.5% | 40.4% |

如果三维的成本也是纯固定成本 `F`，单帧成本应基本不变（每次更新付同样的钱），累计时间应随更新次数减少而下降。实际相反：**单帧成本随批量上升 3.3 倍，累计时间反而增加 72%**。

这说明三维存在明显的、随批量增长的单批成本，`P` 不可忽略。与二维形成结构性差异。

### 4. 三维的额外成本位置随批量前移

三阶段的对比暴露了两者的另一个差异：

```text
二维 startTime → renderStart 中位：0.5 / 0.6 / 0.6 / 0.2 / 0.3 ms   → 基本不随 batch 变化
三维 startTime → renderStart 中位：3.2 / 27.4 / 39.7 / 52.7 / 83.4 ms → 随 batch 单调上升
```

按 3.1 节对第一阶段的定义（进入 rendering cycle 之前的主线程工作），三维在批量变大时，回调之前的工作量显著增加（P95 从 47.3 ms 升到 268.6 ms）。合理的解释是批量内每个点都要走一遍 Cesium 侧的 Entity / 柱体更新与 `Cartesian3` 构造，这部分工作在批量大时集中出现。**这是基于阶段划分的推断，尚未取得该区间内的函数级归因**。

第二阶段的中位数三维反而从 156.7 降到 107.7，与二维 batch = 20 的表现一致——固定开销被摊薄。真正恶化的是第二阶段的 **P95**（209.7 → 653.1 ms），即少数帧的尖峰。

### 5. 最优 batch 的判断

按 3.6 节的标准——「刚好能够稳定追平输入、同时不显著恶化的最小充分 batch」：

**二维：batch = 10**

```text
batch 10：消费 1180 = 接收 1180，pending 0，FPS 46.19，LoAF P95 361.9 ms
batch 20：消费 1180，pending 0，FPS 54.94，LoAF P95 302.1 ms
```

batch = 10 已满足「消费能力 ≥ 20 点/秒」且「pending 不再增长」。batch = 20 的 FPS 更高、LoAF 反而更短，但收益已明显递减（FPS 46 → 55，仅 +19%），且它会进一步增加数据聚合等待时间。因此二维的推荐点是 **10**，20 可作为流畅度优先时的备选。

**三维：batch = 20**

```text
batch 10：消费 1060，pending 100（未完全追平）
batch 20：消费 1140 = 接收 1140，pending 0
```

三维要到 batch = 20 才能清空队列，但代价是 FPS 7.47、LoAF P95 739 ms——**比 batch = 1 时更卡**。也就是说三维不存在一个「既追平输入又保持流畅」的批量：

```text
batch 小 → 页面相对不那么卡（9.07 FPS），但队列持续积压
batch 大 → 队列追平，但页面更卡（7.47 FPS）、长帧更长（P95 739 ms）
```

这不是调参能解决的，与 3.7 节假设的推论一致：三维需要继续深入 Cesium 侧的单批成本（Entity / 几何 / 绘制准备），而不是继续加大 batch。

### 6. 边界

- 本次仍是约 60 秒的 headless Chrome 实验，用于比较批量响应结构，不能代替目标设备的最终验收，也未覆盖长时间运行后的内存与可视对象增长。
- 组间接收点数在 1140～1180 之间波动（受自然秒批次与采样边界影响），三维 batch = 5/10 的模拟器生成数为 1220 而非 1200，属采样窗口边界，不影响趋势判断。
- 每组只运行一次，未按 3 次取中位数。因此**趋势可信，单点数值不宜作为精确阈值**；尤其三维 batch = 1 的最大长帧 1032 ms 是单次尖峰，不代表稳定水平。
- 二维在 batch = 20 时第一阶段 P95 出现 88.0 ms 的跳变（其余组 ≤ 7.6 ms），是单组偶发，需要重复实验确认。

## 复用方法

在仓库根目录运行，先启动本地前后端并提供 `QHZHC_BENCH_PASSWORD`：

```powershell
$env:QHZHC_BENCH_MAP_TYPE = '1'      # 1 = 二维，2 = 三维
$env:QHZHC_BENCH_FRAME_LIMIT = '10'  # 唯一自变量：每帧消费点数
$env:QHZHC_BENCH_OUTPUT = 'reports/realtime-rendering/batch-2d-b10'
node scripts/measure-realtime-loaf.mjs
```

脚本会在采样前清空可视历史，保证每组起点为 0；`QHZHC_BENCH_FRAME_LIMIT` 省略时回到每帧 1 点，与既有二维/三维基线口径一致。
