# 历史规模对实时渲染的影响：0 / 200 / 500 / 1000 / 3000 / 5000 / 8000 点

对应 [优化过程.md](../../docs/优化过程.md) 第 2 章的 H3 假设（历史增长造成退化）与第 3 节的验收标准。本轮固定实时输入，只改变**采样开始前地图上已有的历史点数**，观察二维与三维在持续实时渲染下的表现。

## 实验条件

```text
服务端生成速率：20 点 / 秒
订阅档位：1 点 / 秒（脚本强制要求 rate = 1 与 batch = 1 才允许运行流式对照）
渲染模式：每帧 1 点
历史起点：0 / 200 / 500 / 1000 / 3000 / 5000 / 8000 个可视点
持续时间：约 60 秒
浏览器：Chrome headless，1440 × 900
```

历史点由脚本调用 `/api/telemetry/latest?limit=N` 取真实遥测点注入；每种规模在采样前都会核对**物理渲染对象数**等于注入点数（各组 `pointRetentionPass` 均为 true），并把地图可视历史清空后重新全量绘制，确保起点条件一致。

## 一个必须先说明的方法学问题

第一版 fixture 直接按「最近 N 点」逐个规模取，结果**完全被地理位置主导**：

| 二维 3000 点 | 路线所属时段 | FPS 均值 |
| --- | --- | --- |
| 第一版（各取最近 N 点） | 19:23 段 | 13.68 |
| 第二版（同源嵌套） | 19:10 段 | **138.18** |

同样的 3000 点，只因取自不同时间段的轨迹（经度 98.5 / 103.9，而地图中心是 104.8），FPS 相差 10 倍。同理，5000 点那版落在 17:12 段，FPS 只有 5.35，也与点数无关。

原因是「历史点数」天然耦合了「轨迹的地理位置与跨度」：取的点越多，覆盖的路线越长、位置越远，地图视角与可见要素随之改变。

因此本报告全部采用**同源嵌套 fixture**：所有规模都取自同一段真实路线（2026-09-23 19:10–19:27）的前 N 个点，保证地理位置同源，只改数量。生成物在 [fixtures/](./fixtures/) 下。

## 分析

### 1. 二维：历史 0 → 8000 对实时帧率几乎没有影响

二维 FPS 均值集中在 **132 ～ 151** 之间，且**没有单调趋势**：

```text
  0 点 131.67
200 点 149.13
500 点 147.29
1000 点 150.84
3000 点 138.18
5000 点 139.96
8000 点 132.96
```

把历史点从 200 加到 8000（40 倍），FPS 只从 149.13 变到 132.96（-10.8%），且 0 点那组还略低于 200 点。这与第 2 章 H3 假设要求的「≥15% 的稳定差异」不符。

原因与渲染方式有关：二维用 OpenLayers + Canvas，要素以图层为单位统一绘制，且 Canvas 渲染器会跳过视野外要素；新增的历史浓度点与轨迹段对单帧成本的影响远小于其数量增长。

**注意**：FPS 稳定不代表长帧不变。LoAF P95 随历史增长明显上升（74.2 → 949.3 ms），最大长帧也从 82 ms 涨到 949 ms。也就是说：**二维的"平均流畅度"不受历史影响，但偶发卡顿会随历史变大**。5000/8000 组的 FPS 最小值掉到 43.75 / 4.97，就是这些长帧造成的。

### 2. 三维：历史规模与实时帧率强负相关

三维从 200 点开始呈**清晰单调下降**：

| 历史点数 | 200 | 500 | 1000 | 3000 | 5000 | 8000 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| FPS 均值 | 122.49 | 131.23 | 114.32 | 96.61 | 66.05 | 48.31 |
| FPS 最小 | 92.46 | 104.40 | 41.95 | 8.95 | 16.69 | 0.92 |
| Cesium 回调次数 | 5 | 4 | 14 | 25 | 56 | 108 |
| Cesium 回调累计 | 344 ms | 188 ms | 364 ms | 477 ms | 1714 ms | 4823 ms |
| LoAF 次数 | 21 | 23 | 30 | 28 | 59 | 120 |

对比 200 点与 8000 点：

```text
FPS 均值        122.49 → 48.31   (-60.6%)
Cesium 回调次数      5 → 108     (21.6 倍)
Cesium 回调累计   344 ms → 4823 ms (14 倍)
LoAF 次数           21 → 120     (5.7 倍)
```

机制与第 4 章的结论一致：三维每个可视点都是一个独立 Cesium Entity（柱体），轨迹按 256 点分段成多个 polyline。历史规模越大，Scene 里需要更新和遍历的对象越多，Cesium 的 `FrameRequestCallback` 被触发得越频繁、累计耗时越长，可用帧随之减少。

这**支持 H3 假设在三维侧成立**，也解释了第 4 章降采样实验为何有效——降采样直接减少进入 Cesium 的对象数。

### 3. 二维与三维的差异可以量化

同一历史规模下两者的 FPS 比值：

| 历史点数 | 200 | 500 | 1000 | 3000 | 5000 | 8000 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 二维 FPS | 149.13 | 147.29 | 150.84 | 138.18 | 139.96 | 132.96 |
| 三维 FPS | 122.49 | 131.23 | 114.32 | 96.61 | 66.05 | 48.31 |
| 三维 / 二维 | 0.82 | 0.89 | 0.76 | 0.70 | 0.47 | 0.36 |

小历史（200–500 点）时两者接近；历史超过 1000 点后三维迅速落后，8000 点时只有二维的 36%。

**这说明历史规模的成本主要在三维侧，而且是非线性的。**

### 4. 对 H3 假设与验收标准的回答

第 2 章 H3 的判定门槛是「历史规模扩大后，渲染 P95、真实 FPS 或内存出现至少 15% 的稳定差异」。

- **二维：不满足**。FPS 差异仅 -10.8%，且非单调，不足以支持对二维施加历史限制。
- **三维：满足**。1000 → 8000 点 FPS 从 114.32 降到 48.31（-57.8%），远超 15% 门槛，趋势单调且与 Cesium 回调次数同步。

由此本轮的结论是：

> **历史规模是三维的瓶颈变量，不是二维的。对二维无需按历史点数做淘汰；对三维需要限制进入场景的对象数。**

### 5. 三维可用规模的参考区间

按第 3 节「真实 FPS 不低于同页面空闲基准 90%」的思路，用三维 200 点的 122.49 FPS 作为近似基准：

| 历史点数 | FPS | 相对 200 点 | 是否 ≥90% 基准 |
| ---: | ---: | ---: | --- |
| 200 | 122.49 | — | 基准 |
| 500 | 131.23 | 107% | 是 |
| 1000 | 114.32 | 93% | 是 |
| 3000 | 96.61 | 79% | 否 |
| 5000 | 66.05 | 54% | 否 |
| 8000 | 48.31 | 39% | 否 |

即在本实验的 1 点/秒 输入下，三维历史规模**控制在 1000 点以内**才能接近基准帧率。

## 边界

- 每组只运行一次，未按第 3 节要求的三轮取中位数。趋势方向明确（三维单调、二维平稳），但**单点数值不宜当作精确阈值**。
- 嵌套 fixture 只解决了「地理位置同源」，没有解决「地理跨度」：200 点跨 0.4 km，8000 点跨 15.8 km。所以「历史点数」仍与「轨迹跨度」耦合。要完全分离这两者，需要让每组的历史点覆盖**相同跨度、不同密度**（例如对 8000 点均匀抽样到 N 点）。
- 实验输入是 1 点/秒。在更高输入速率下，历史规模与实时负载会叠加，结论不能直接外推。
- 仍未覆盖长时间运行的内存与 GC 行为；本轮最多只观测到 60 秒内 8059 个可视点。
- 三维 0 点基线因缺少预热阶段不可与其余组直接比较。

## 复用方法

```powershell
$env:QHZHC_BENCH_PASSWORD = '...'
$env:QHZHC_BENCH_MAP_TYPE = '2'                                    # 1 = 二维，2 = 三维
$env:QHZHC_BENCH_POINT_LIMIT = '1'                                 # 订阅 1 点/秒
$env:QHZHC_BENCH_FRAME_LIMIT = '1'                                 # 每帧 1 点
$env:QHZHC_BENCH_HISTORY_COUNT = '3000'
$env:QHZHC_BENCH_FIXTURE = 'reports/realtime-rendering/fixtures/history-3000.json'
$env:QHZHC_BENCH_PHASE = 'baseline'
$env:QHZHC_BENCH_OUTPUT = 'reports/realtime-rendering/hn3000-singlepoint-2026-09-24/baseline-2d'
node scripts/measure-realtime-loaf.mjs
```

不提供 `QHZHC_BENCH_FIXTURE` 时，脚本会自动从 `/api/telemetry/latest?limit=N` 取点，但该接口上限为 5000（[app.ts](../../QHZHC_Server/src/server/app.ts) 的 `Math.min(5_000, ...)`），因此 8000 点需要预先生成 fixture 文件。生成方式：直接从 `QHZHC_Server/.data/qhzhc.sqlite` 的 `telemetry` 表按 `sequence` 倒序取 N 行、反转成正序、按 `toLegacyPoint` 映射（本仓库的 [fixtures/history-8000.json](./fixtures/history-8000.json) 即由此生成），其余规模由它取前 N 点派生，以保证同源。
