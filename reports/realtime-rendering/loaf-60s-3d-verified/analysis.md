# 实时渲染 1 点/帧、20 点/秒：三维地图 FPS 与 LoAF 实测

## 条件和产物

- 正式采样：2026-09-23，Chrome headless（`--headless=new`），1440 × 900，三维地图（Cesium，`scene3DOnly: true`），实际采样 60.05 秒。
- 渲染模式：手动每帧 1 点；订阅：全部接收；模拟器：路线走航、每秒 20 点。脚本在结束后恢复原模拟器配置与运行状态。
- **本次起始可视点为 0，是空白冷启动场景。** 采样前模拟器处于暂停状态（最后一次生成时间比采样开始早约 20 分钟），进入实时模式时最近五分钟窗口为空，地图从空白起步。这一点与[二维正式复测](../loaf-60s-verified/analysis.md)的 239 点起步不同，因此**横向比较必须使用二维冷启动参考**，不能直接对二维正式复测的数字。
- 本次采样与二维共用同一入口脚本；三维通过环境变量切换，不新增脚本：[measure-realtime-loaf.mjs](../../../scripts/measure-realtime-loaf.mjs)（`QHZHC_BENCH_MAP_TYPE=2`）。
- [原始逐秒 FPS、运行指标和逐条 LoAF](./raw.json)、[机器摘要](./summary.json)、[采样结束截图](./dashboard.png)、[模拟器恢复核对](./restoration.json)。

## 分析

### 1. 首次取得脚本级归因，且全部指向 Cesium 的动画帧回调

二维正式复测中 323 条长帧的脚本归因为空，只能停在「耗时在样式计算开始之前」这一层级。三维本次 343 条长帧**全部**带有脚本条目，并且归因高度集中：

- `sourceURL`：`http://127.0.0.1:9527/static/Cesium/Cesium.js`
- `sourceCharPosition`：4500403（压缩后函数名 `n`）
- `invoker` / `invokerType`：`FrameRequestCallback` / `user-callback`
- 出现次数 343 次，累计 14068.4 ms

343 次与 343 条长帧一一对应，说明每个长帧里都有一个 Cesium 注册的 rAF 回调在执行，累计占用约 14.1 秒，占总采样时长 60.05 秒的 **23.4%**；单条中位 37.7 ms、P95 61.4 ms、最大 955.5 ms。

最长的一帧 `duration` 为 1032 ms，其中该回调独占 955.5 ms：`renderStart` = 4756.1，`styleAndLayoutStart` = 5777.6，脚本从 `renderStart` 处开始执行。因此三维超长帧的直接来源是 Cesium 渲染循环本身，而不是 Vue 组件提交或 ECharts 更新。

需要限定的是：`sourceFunctionName` 是生产构建压缩后的 `n`，只能定位到「Cesium.js 中的这个 rAF 回调条目」，不能凭它指认 Cesium 内部具体哪个子系统（瓦片调度、几何批处理或着色器准备）。要再细一层，需要带 source map 的 Performance trace。

### 2. 额外开销集中在帧的前置区间，且是长尾形态

三维的 `startTime → renderStart` 从二维的中位 0.5～0.8 ms 升到 3.2 ms，**P95 从 5.3～5.5 ms 升到 47.3 ms**，接近 9 倍。这个区间包含 rAF 回调等帧内前置工作，与上面 Cesium rAF 回调的证据一致。

反观 `styleAndLayoutStart → 帧结束`，三份数据的中位都是 0.4 ms、P95 都不超过 0.7 ms。因此本次数据同样**不支持**「DOM 布局是主要耗时」的判断——三维把成本同样压在样式计算开始之前。

均值口径容易误导，这里以分位数为准：`startTime → renderStart` 的均值（15.5 ms）远高于中位数（3.2 ms），说明该区间是被少数长帧拉高的长尾，而非整体性上移。

### 3. 瓶颈在绘制侧，队列积压只是其结果

三维与二维冷启动在相同输入（20 点/秒、每帧 1 点、全部接收）下都出现持续积压，且三维更严重。这再次印证队列模型 `μ = 消费帧数 × 每帧点数`：每帧 1 点时消费能力完全由「每秒能产出多少个可用的消费帧」决定，而 Cesium 的 rAF 回调把大量帧拉长到 50 ms 以上——343 条长帧对约 544 次 rAF 调用（9.07 FPS × 60 s），即约 63% 的帧属于长帧。

提高每帧批量仍然是缓解方向，但三维的批量成本曲线必须重新测量：Cesium 侧的单帧成本已经出现 1 秒级尖峰，盲目增批有放大长帧的风险，因此第 3 节「半帧预算限制单批成本」的约束在三维下更关键。

### 4. 不能从本次数据得出的结论

- **不能**据此宣称三维比二维「性能更差」到某个固定倍数：两次采样的浏览器进程状态、Cesium 首次加载与着色器编译时机不同，只有消费速率和长帧结构的差异有同口径支持。
- **不能**把 1032 ms 当作稳定态的代表值：它是单次最大值，中位长帧为 166.2 ms。是否稳定出现需要更长时间观测。
- **不能**判断目标设备上的表现：headless Chrome 的数字不直接等同于目标机器验收值，且本次为 60 秒短窗，未覆盖内存与可视对象的长期增长。
- **不能**由「二维脚本归因为空」推断二维没有脚本耗时：归因为空是 LoAF 归因机制未命中，不是「无脚本执行」的证据。

## 复用方法与口径

在仓库根目录运行，先启动本地前后端，并在进程环境中提供 `QHZHC_BENCH_PASSWORD`：

```powershell
$env:QHZHC_BENCH_MAP_TYPE = '2'
$env:QHZHC_BENCH_OUTPUT = 'reports/realtime-rendering/loaf-60s-3d-verified'
node scripts/measure-realtime-loaf.mjs
```

`QHZHC_BENCH_MAP_TYPE` 省略或为其他值时回到二维，其余口径（60 秒、1 点/帧、20 点/秒、全部接收）与二维一致，二维历史结果不受影响。三维模式下脚本会先把页面切到 3D 并等待 Cesium Viewer 就绪，再进入计时，避免把 Viewer 初始化与着色器编译算进采样窗口。

两点口径说明：

- 三维组件由 `v-if` 创建，二维组件由 `v-show` 隐藏，但二维组件的批次 watcher 带有 `mapType !== 1` 守卫（[PlanimetricMap.vue](../../../QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)），因此三维采样期间只有 Cesium 在绘制，不存在两个地图叠加绘制。
- 本次采样要求 `emptyRender` 为 `false`。该开关为 true 时数据取出后不写入响应式状态，测到的是空渲染成本，不能用于三维绘制结论。
- 这里的 FPS 是浏览器 rAF 回调频率，不能直接等同于实际提交到屏幕的帧数。LoAF 只记录达到 50 ms 门槛的长帧；低于 50 ms 的掉帧及 GPU 合成等问题仍需 Performance trace 核对。
