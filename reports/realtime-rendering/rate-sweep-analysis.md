# 降低每秒接收量实验：订阅 1/2/5/10 对二维与三维的影响

对应 [优化过程.md](../../docs/优化过程.md) 第 4 章的降采样方向（4.12 假设、4.14 依据、4.18 设计、4.19 指标、4.20 判断方法）。本轮要回答的是：

> 通过减少单位时间实际进入可视化的数据量，能否得到比单纯增大批量更好的性能表现？即假设「N（单位时间进入可视化的点数）是当前三维瓶颈的重要变量」是否成立。

## 实验条件

固定不变：

```text
服务端生成速率：20 点 / 秒（脚本强制写入并在采样前后各校验一次）
历史起点：0 个可视点（冷启动，采样前显式清空）
测试时间：约 60 秒
浏览器：Chrome headless，1440 × 900
```

唯一自变量：**订阅档位 rate ∈ {1, 2, 5, 10, 20}**，即服务端每秒下发给该连接的点数上限；同时**渲染模式 batch 取与 rate 相同的值**，因此每秒约触发 1 次地图更新。二维与三维分别独立运行。

与第 3 章批量实验的区别：

```text
第 3 章：rate 固定 20，只改 batch          → 只减少地图更新次数 K
本轮  ：rate 与 batch 同值一起降            → 同时减少进入可视化的点数量 N 和更新次数 K
```

这一点在下面的「边界」中会再次说明。

## 分析

### 1. 降低接收量对二维和三维都有效，且三维收益更大

从 rate = 20 降到 rate = 1：

```text
              二维                三维
FPS 均值    54.94 → 143.35       7.47 → 44.08
            (2.6 倍)             (5.9 倍)
LoAF P95   302.1 → 61.2 ms      739.2 → 93.2 ms
            (-79.7%)            (-87.4%)
LoAF 最大   681.8 → 61.2 ms      979 → 146.4 ms
Cesium 回调    —               24234 → 1123 ms
                                (-95.4%)
```

三维的改善幅度明显大于二维，这符合第 3 章的观察——三维的成本里有一大块与数据规模直接相关。

### 2. 关键对比：固定 batch，只降 rate

为了把「接收量」的效应从「批量」中分离出来，比较**相同 batch、不同 rate** 的两组数据（左侧来自本轮，右侧来自第 3 章批量实验）：

二维：

| batch | rate = batch（本轮） | rate 固定 20（第 3 章） | 倍数 |
| ---: | ---: | ---: | ---: |
| 1 | 143.35 | 10.49 | **13.7×** |
| 2 | 140.12 | 12.83 | **10.9×** |
| 5 | 109.06 | 25.51 | 4.3× |
| 10 | 71.76 | 46.19 | 1.6× |
| 20 | 54.94 | 54.94 | 1×（同组） |

三维：

| batch | rate = batch（本轮） | rate 固定 20（第 3 章） | 倍数 |
| ---: | ---: | ---: | ---: |
| 1 | 44.08 | 9.07 | **4.9×** |
| 2 | 34.33 | 8.50 | **4.0×** |
| 5 | 16.18 | 6.75 | 2.4× |
| 10 | 9.62 | 6.85 | 1.4× |
| 20 | 7.47 | 7.47 | 1×（同组） |

在每帧点数完全相同的前提下，仅仅把每秒接收量降下来，就能获得数倍改善。**这说明接收量（N）是比更新次数（K）更强的变量。**

### 3. 两条优化路径的对比：降总量远优于加大批量

以三维为例，从同一初始状态出发：

```text
路径 A：只增大 batch（rate 固定 20）
  9.07 FPS (batch = 1)  →  7.47 FPS (batch = 20)
  结果：吞吐上去了，FPS 反而下降

路径 B：降低 rate（batch 同值）
  7.47 FPS (rate = 20)  →  44.08 FPS (rate = 1)
  结果：FPS 提升 5.9 倍，队列保持清空
```

第 3 章的结论是「三维继续加大 batch 已经没有收益」；本轮给出了可替代的方向：**减少实际进入可视化的数据量，比调整批量有效得多**。这与 4.13 节的判断一致——batching 解决 `K`，降采样解决 `N`，而当前 `N` 才是主导项。

### 4. 逐条核对 4.20 的判断标准

4.20 提出：若 rate 从 20 降到 1 能稳定观察到第一阶段 P95 ↓、Cesium callback ↓、第二阶段 P95 ↓、LoAF P95 ↓、FPS ↑，则假设成立。

| 指标（三维） | rate 1 | 2 | 5 | 10 | 20 | 是否单调下降 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 第一阶段 P95 | 63.5 | 36.6 | 90.2 | 196.7 | 268.6 | 基本下降（1/2 处反转） |
| Cesium 回调累计 | 1123 | 2702 | 16095 | 15978 | 24234 | 下降（5/10 接近持平） |
| Cesium 回调单帧均值 | 13.7 | 17.3 | 35.5 | 57.5 | 134.6 | **严格单调下降** |
| 第二阶段 P95 | 71.2 | 69.2 | 133.6 | 250.5 | 653.1 | 基本下降（1/2 持平） |
| LoAF P95 | 93.2 | 84.3 | 192.1 | 421.6 | 739.2 | 基本下降（2 略优于 1） |
| FPS 均值 | 44.08 | 34.33 | 16.18 | 9.62 | 7.47 | **严格单调下降** |

除 rate = 1 与 2 之间的轻微反转外，各项指标都随接收量下降而改善，且在最强的两项（FPS、Cesium 单帧成本）上完全单调。

> **假设成立**：单位时间进入 Cesium 的数据点数量，确实是当前三维性能瓶颈的重要组成部分。

### 5. 但三维存在第二层瓶颈：44 FPS 的天花板

假设成立不等于问题解决。同样把接收量降到 1 点/秒：

```text
二维：143.35 FPS   ≈ 空闲基准（约 120 以上）
三维：44.08 FPS    仅为二维的 1/3.3
```

三维在 1 点/秒时仍有 82 个 LoAF、Cesium 回调累计 1123 ms。也就是说，**即使把数据量压到最低，三维仍有与数据量无关的固有成本**——这部分来自 Cesium 场景自身的持续开销（Scene 更新、地形与影像、Camera 等），对应 4.20 后半段提示的排查方向（Entity 模型、`CallbackProperty`、Primitive、Camera、Scene update/render）。

因此后续优化需要分两层：

```text
第一层（已验证有效）：控制 N —— 降低进入可视化的点数
第二层（尚未解决）：Cesium 场景固有成本 —— 即使 N 很低也存在的基线开销
```

### 6. 对生产方案的含义

- 4.16 节强调正式方案不能简单「每 N 个点取一个」，必须保留轨迹形态、浓度异常与最大等待时间。本轮只验证了「降低 N 有收益」，**没有验证采样规则本身**，两者不能混为一谈。
- 从本轮数据看，二维在 rate = 5 时已有 109 FPS、LoAF P95 < 100 ms；三维要到 rate ≈ 1～2 才进入 34～44 FPS。若要设定「最低需要降到多少」，二维与三维应当分开取值。
- 三维即使降到 1 点/秒也未恢复到二维水平，说明单靠降采样不足以让三维达标，需要与 Cesium 场景优化配合。

### 7. 边界

- **N 与 K 未完全分离**：本轮 rate 与 batch 同值，因此每秒点数 N 和更新次数 K 同时下降。第 2 节的「固定 batch、只降 rate」交叉对比能支持 N 是主导因素，但严格分离仍需按 4.18 的原设计再跑一轮「batch 固定为 1、只降 rate」。
- **每组仅运行一次**，未按第 3 节要求的三轮取中位数；趋势可信，单点数值不宜当作精确阈值。
- 三维 rate = 5 的 LoAF 次数（453）高于 rate = 10（278），与整体趋势不符，属单组波动，需要重复实验确认。
- 三维 rate = 10 结束时剩 10 点待消费，说明该档位下消费刚好略低于输入，处于临界状态。
- 采样期间发现模拟器管理页面（[simulatorAdmin.vue](../../QHZHC_Web/src/views/Admin/simulatorAdmin.vue)）可随时改写服务端生成速率，曾把 20 改成 5 导致一组数据作废。现在脚本会在采样前强制写入 20 点/秒并校验、采样后再次校验，`serverGenerated` 已全部回到 1200 量级。**做同类实验时需注意该页面会干扰生成速率。**
- 仍是约 60 秒的 headless Chrome 实验，不能代替目标设备的最终验收，也未覆盖长时间运行后的内存与可视对象增长。

## 复用方法

```powershell
$env:QHZHC_BENCH_MAP_TYPE  = '2'   # 1 = 二维，2 = 三维
$env:QHZHC_BENCH_POINT_LIMIT = '5' # 订阅档位：服务端每秒下发点数上限
$env:QHZHC_BENCH_FRAME_LIMIT = '5' # 渲染模式：每帧消费点数，本轮与上一项同值
$env:QHZHC_BENCH_OUTPUT = 'reports/realtime-rendering/rate-3d-r5'
node scripts/measure-realtime-loaf.mjs
```

`QHZHC_BENCH_POINT_LIMIT` 省略时表示全部接收，与既有基线口径一致。脚本会强制把服务端生成速率固定为 20 点/秒，并在采样前后校验，避免管理页面改写造成的组间漂移。
