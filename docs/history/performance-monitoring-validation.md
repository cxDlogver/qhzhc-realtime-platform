# 性能监控验收记录

验证日期：2026-09-07。功能链路已实现，**本轮开销验收尚未全部通过**。不将既有业务渲染性能问题算作监控功能失败，也不将监控上线等同于业务指标达标。

## 验证环境与范围

- Windows，Intel Core i7-14650HX，24 个逻辑处理器，约 31.7 GiB RAM。
- 已安装的前台 Chrome 152.0.7977.82，1440 × 1000 视口，Node 24.19.0。
- 生产构建，本地 Express 与独立 SQLite 数据库，未使用用户的业务数据库。
- 六轮交替关闭/开启监控，每轮五分钟，20 点/秒；由独立 rAF 探针按每 30 秒采样五秒测量，各图表使用相同的外部同步调用计时。
- 所有六轮采样窗口均报告前台可见且有焦点；三个开启轮次各有 32 次成功上报，均返回 204，没有浏览器页面异常。

## 自动化与界面验证

- 类型检查通过；前端 114 项 / 15 套测试通过，服务端 38 项 / 8 个文件通过，集成测试 8 项通过。
- 生产构建通过。已有字体、vendor 与 Cesium 大资源产生的体积警告仍存在。
- 最终 Chrome 功能冒烟：15 次监控上报均为 204，页面脚本异常为零；SPA 进入与直接刷新归属分别验证。
- 测试脚本注入首次接口 401、后续 600 ms 延迟、250 ms 主线程阻塞、断网/恢复及标签页切换。API 尝试次数、耗时、事件循环延迟、断连记录均可观察；LoAF 百分比不超过 100。
- 看板、指标说明抽屉、访问详情已打开并检查截图。测试期间的故障注入没有进入生产业务代码。
- BFCache 实测：Chrome 的 pageshow.persisted 为 true，恢复后的 documentId/viewId 均更新，无页面异常；见 [BFCache 原始结果](../reports/performance-monitoring/bfcache-results.json)。测试按导航提交等待，避免把 BFCache 不触发新的 load 误判为恢复失败。
- 浏览器脚本使用新建隔离数据库及仅存内存的随机测试密码，不修改现有账号。

### 3D 与 DevTools 交叉检查

| 压力档 | 时长 | 数据点数（开始 → 结束） | FPS 采样情况 |
|---|---:|---:|---|
| 20 点/秒 | 301.1 秒 | 852 → 5,828 | 10 个有效前台窗口，约 6.06 逐步降至 0.94 |
| 100 点/秒 | 30.5 秒 | 5,828 → 8,062 | 1 个有效前台窗口，约 0.89 |
| 500 点/秒 | 31.0 秒 | 8,162 → 12,265 | 1 个有效前台窗口，约 0.69 |

100/500 点档属于短时压力诊断，不是稳定性或开销预算验收。数据量变化也说明压力档输入不等于页面实际消费速率；本轮未把未消费输入伪装成已绘制数据。

前台 Chrome 的 15 秒 DevTools trace 中，最长 FireAnimationFrame 约 311.28 ms，最长 MajorGC 约 213.31 ms，支持主线程存在长阻塞的判断。嵌套事件的耗时不可相加为 CPU 使用率；该录制不属于六轮 A/B 窗口。

初版验证脚本在六轮结束后误关工具栏，3D 按钮等待超时；修正脚本后保留原六轮结果，独立续跑并完成 trace 与三个 3D 压力档，没有把该脚本失败计作产品失败。

## 使用与限制

管理员通过 /#/admin/performance 打开看板，也可从模拟后台入口进入。指标解释、阈值来源、采样边界和 API 见 [实现与使用说明](./performance-monitoring-implementation.md)。

真实浏览器脚本保存在 scripts/performance-browser-validation.mjs。原始运行记录、截图和 DevTools trace 位于本地忽略目录 .performance-work，提交用摘要保存在 reports/performance-monitoring。

浏览器关闭阶段的 keepalive 上报是尽力传输；缺失记录不补零。后台在不足 20 次同组访问时不作总体判断。业务首屏从路由进入开始，场景切换取消原任务，因此默认 2D 入口切换为 3D 后不会生成一条冒充路由首屏的 3D ready 样本；3D 持续更新耗时仍会记录。资源或外部地图不可用时需单独解释，不能将地图瓦片下载完成等同于业务首屏绘制。
