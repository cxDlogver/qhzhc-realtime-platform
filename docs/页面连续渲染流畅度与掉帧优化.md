## 1. 工作目标与实时渲染主链

### 【实时可视化的核心目标不是“收到数据”，而是持续把最新数据稳定地呈现出来】

#### <u>实时链路存在“数据可靠到达”和“页面持续流畅”两条独立主线</u>

QHZHC 的实时页面同时承担：

- WebSocket 持续接收走航车遥测；
- 折线图更新气体与气象趋势；
- 二维 OpenLayers 地图更新车辆位置、浓度点和轨迹；
- 三维 Cesium 地图更新车辆、柱体和轨迹；
- 用户仍然需要拖拽、切换气体、切换二维/三维和查询历史数据。

因此系统不能只回答：

> 数据有没有通过 WebSocket 到达浏览器？

还必须继续回答：

> 数据到达以后，浏览器能不能持续按用户可接受的节奏把它画出来？

两条主线可以分开理解：

~~~text
Reliable Realtime Transport
WebSocket → Replay → Queue
解决：
数据能否连续到达
        ↓
Continuous Rendering
Queue → State → Map / Chart → Frame
解决：
到达的数据能否持续流畅呈现
~~~

如果第一条正常、第二条失效，会出现一种非常典型的“假实时”：

~~~text
服务端持续推送
WebSocket 也没有断
        ↓
前端处理不过来
        ↓
Queue 越积越多
        ↓
用户仍然看到画面变化
但看到的是越来越旧的数据
~~~

所以本项目把“页面流畅度”放在实时链路的核心位置，不只是为了视觉效果，而是为了同时保证：

- **Visual Continuity（视觉连续性）**：地图移动、轨迹增长和图表变化不能频繁冻结；
- **Data Freshness（数据新鲜度）**：页面不能因为积压越来越滞后；
- **Interaction Responsiveness（交互响应）**：持续推流时仍要能拖拽、点击和切换；
- **Long-running Stability（长期运行稳定性）**：页面运行时间增长后不能持续退化。

#### <u>当前实时数据从 WebSocket 到画面经过完整的生产消费链</u>

当前代码中的主链是：

~~~text
Server telemetry_second                  // 服务端按"自然秒"推送的批次（bucket 起点/状态/points）
        ↓
RealtimeClient.handleTelemetrySecond()   // 校验自然秒对齐与 bucket 边界；处理补发与缺口；更新已接收批次指针
        ↓
FrameTelemetryQueue.enqueue()            // 把本批点追加进帧队列并调度下一帧（接收不等待渲染）
        ↓
requestAnimationFrame                    // 与屏幕刷新对齐的下一帧回调
        ↓
FrameTelemetryQueue.flush()              // 每帧按 maxPerFrame 与时间预算取点，回调 onFrame
        ↓
RealtimeClient.publishFrame()            // 把本帧点转成 legacy 信封（code/data），交给页面层 onPacket
        ↓
dataVisualization.handleRealtimePacket() // 校验信封 → 增量并入图表/地图 → 刷新详情卡与天气
        ↓
┌────────────────────────────┐
│ Chart data                 │           // 折线图：按时间窗口保留
│ Map realtime batch         │           // 地图轨迹：全量保留（无上限）
│ Detail card                │           // 详情卡：取本批最后一个点
│ Weather latest point       │           // 天气：取本批最后一个点
└────────────────────────────┘
        ↓
Vue component update                     // 响应式状态变更触发组件重渲染
        ↓
ECharts / OpenLayers / Cesium            // 图表 / 2D 地图 / 3D 地图渲染库
        ↓
Browser Rendering                        // 浏览器绘制管线（样式 → 布局 → 绘制 → 合成）
        ↓
Screen                                   // 最终呈现到屏幕
~~~

源码入口：

- [realtimeClient.ts](../QHZHC_Web/src/views/DataVisualization/services/realtimeClient.ts)
- [FrameTelemetryQueue.ts](../QHZHC_Web/src/views/DataVisualization/services/FrameTelemetryQueue.ts)
- [dataVisualization.vue](../QHZHC_Web/src/views/DataVisualization/dataVisualization.vue)
- [Charts.vue](../QHZHC_Web/src/views/DataVisualization/components/Charts.vue)
- [PlanimetricMap.vue](../QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)
- [StereoscopicMap.vue](../QHZHC_Web/src/views/DataVisualization/components/StereoscopicMap.vue)

整个优化工作的关键，就是逐层判断：

> **到底是哪一步让页面无法继续按帧推进？**

关键链路在当前源码中不是概念图，而是下面这组真实调用：

```ts
// realtimeClient.ts
case "telemetry_second":
  this.handleTelemetrySecond(message);
  return;

private handleTelemetrySecond(message) {
  ...
  if (message.points.length > 0) {
    this.rateWindowReceived += message.points.length;
    this.totalReceived += message.points.length;
    this.frameQueue.enqueue(message.points);
    this.nextRenderPoint = this.frameQueue.peekNext();
  }
  ...
  this.frameQueue.resume();
}

private publishFrame(points: TelemetryPoint[]): void {
  if (!points.length) return;
  this.rateWindowConsumed += points.length;
  this.options.onPacket({
    code: 200,
    message: "ok",
    data: points.map(toLegacyPoint),
  });
}
```

这段代码把链路边界划得很清楚：WebSocket 收到的数据先进入 `FrameTelemetryQueue`，只有 Queue 在某个动画帧真正消费出一批点以后，才通过 `onPacket` 进入页面状态与地图/图表更新。因此 **网络接收频率和页面提交频率从这里开始被解耦**。

## 2. 从“页面卡”到可测量问题：基线、指标与诊断口径

这一阶段先回答：问题是否由持续数据更新触发、应该用什么指标描述，以及瓶颈究竟发生在 Queue、页面提交还是完整 Rendering Frame。

### 【初始问题不是简单的“FPS 低”，而是帧率下降与队列积压形成正反馈】

#### <u>第一阶段先建立无实时负载与持续负载的对照</u>

最早的现象是：停止持续数据更新后页面基本流畅；打开持续输入以后，二维和三维都会出现明显掉帧，并且随着运行继续出现积压。

当前保留的基线实验给出了更明确的数据。

在旧实现、20 点/秒输入、batch=1、约 60 秒的条件下：

| 指标 | 二维 | 三维 |
| --- | ---: | ---: |
| rAF FPS 均值 | 10.49 | 9.07 |
| FPS P5 | 4.19 | 3.95 |
| 接收 / 消费 | 1180 / 414 | 1160 / 342 |
| 结束 Pending | 766 | 818 |
| LoAF P95 | 239.4 ms | 249.5 ms |
| LoAF 最大 | 411 ms | 1032 ms |

证据：

- [二维 LoAF 实验](../reports/realtime-rendering/loaf-60s-verified/analysis.md)
- [三维 LoAF 实验](../reports/realtime-rendering/loaf-60s-3d-verified/analysis.md)

这里已经能够得到第一个关键结论：

~~~text
Arrival Rate
约 20 点/s
        >
实际 Consume Rate
二维约 6.9 点/s
三维约 5.7 点/s
~~~

所以 Pending 必然持续增加。

#### <u>FPS 下降和 Queue 增长会互相放大</u>

当前消费队列由 rAF 驱动：

~~~text
rAF 触发一次
        ↓
最多消费 maxPerFrame 个点
~~~

因此：

~~~text
FPS ↓
        ↓
每秒可用 flush 次数 ↓
        ↓
Consume Rate ↓
        ↓
Pending ↑
        ↓
数据等待更久
并可能让后续状态和场景更重
        ↓
FPS 继续下降
~~~

这不是单纯的“页面偶尔掉几帧”，而是一种可能持续恶化的 Performance Collapse（性能塌缩）。

这也是为什么项目后来同时监控 rAF FPS、arrivalRate、consumeRate、pending、oldestPendingMs 和 queueSlope，而不是只保留一个 FPS。

---

### 【性能定位先抽象为 N、K、C、H、B 五个变量，再设计实验逐个排除】

为了避免直接凭感觉修改代码，整个实时渲染问题可以抽象为五个变量：

| 变量 | 项目中的含义 |
| --- | --- |
| **N：Input Volume** | 单位时间真正进入页面可视链路的数据点数 |
| **K：Update Frequency** | 单位时间触发多少次页面状态 / 地图 / 图表提交 |
| **C：Cost Per Update** | 一次更新本身做多少计算、响应式处理和绘制工作 |
| **H：History / Scene Size** | 页面已经积累多少历史点、Feature、Entity 和轨迹对象 |
| **B：Frame Budget** | 当前设备、刷新率和场景能够提供多少帧预算 |

当前项目中的对应关系：

~~~text
N
→ maxPointsPerSecond
→ 服务端实际推给当前连接多少可视点

K
→ maxPerFrame / batch
→ 同一批数据被拆成多少次页面提交

C
→ Vue Commit
→ ECharts setOption
→ OpenLayers / Cesium 单次更新工作量

H
→ map points
→ Feature / Entity / Route Chunk
→ Chart Window

B
→ actualFps
→ baselineFps
→ frameIntervalMs
~~~

有了这个模型以后，定位问题就不再是“哪个函数看起来慢”，而是先判断：

> **到底应该减少 N、K、C、H 中哪一个，或者当前 B 本来就不足？**

---

### 【第一轮定位先证明瓶颈主要发生在真实绘制链路，而不是队列本身】

#### <u>FrameTelemetryQueue 只负责取点，不代表完整渲染预算</u>

当前队列位于：

[FrameTelemetryQueue.ts](../QHZHC_Web/src/views/DataVisualization/services/FrameTelemetryQueue.ts)

核心逻辑是：

~~~ts
while (
  cursor < queue.length &&
  batch.length < maxPerFrame &&
  (
    batch.length === 0 ||
    now() - startedAt < budgetMs
  )
) {
  batch.push(queue[cursor++]);
}

onFrame(batch);
~~~

这里的 budgetMs = 5 只包围从 Queue 中取出这一批数据，没有包住后面的 Vue 状态更新、Watcher / Props、ECharts、OpenLayers、Cesium 和浏览器绘制。

因此“每帧取点预算只有 5ms”不能被解释成“整个页面每帧只做 5ms 工作”。

#### <u>Empty Render 实验把 Queue 调度和真实绘制拆开</u>

当前 [dataVisualization.vue](../QHZHC_Web/src/views/DataVisualization/dataVisualization.vue) 保留 emptyRender 实验开关。

打开后：

~~~text
Queue 正常消费
        ↓
handleRealtimePacket 正常被调用
        ↓
不写入响应式状态
        ↓
Map / Chart 不更新
~~~

如果空渲染明显恢复，而真实渲染变差，就能够说明：

> Queue 和 rAF 调度不是主要瓶颈，真正成本在后续页面提交与绘制链路。

因此项目没有直接把问题归咎于 WebSocket 或 Queue，而是继续向 Vue、ECharts、OpenLayers、Cesium 方向排查。

---

### 【LoAF 把“页面卡”进一步定位到一整个动画帧，而不是只看 Long Task】

#### <u>rAF FPS 负责看到现象，LoAF 负责解释严重长帧</u>

当前项目使用两套独立机制。

第一套：

[RenderPerformanceMonitor.ts](../QHZHC_Web/src/views/DataVisualization/services/RenderPerformanceMonitor.ts)

通过独立 rAF（requestAnimationFrame）循环统计 actualFps（实测帧率）、baselineFps（基线帧率，取观测到的最高帧率）和 frameIntervalMs（平均帧间隔，毫秒）。

第二套：

[LongFrameDiagnostics.ts](../QHZHC_Web/src/views/DataVisualization/services/LongFrameDiagnostics.ts)

通过 PerformanceObserver 监听 long-animation-frame，并记录 duration、renderStart、styleAndLayoutStart、scripts、forcedStyleAndLayoutDuration、P95 / Max 以及最耗时脚本和 invoker。

MDN 将 LoAF 定义为延迟超过 50ms 的动画帧，并提供脚本和渲染阶段信息用于定位卡顿来源。LoAF 当前仍属于 Limited Availability / Experimental 能力，因此项目中保留 feature detection，不能把它作为唯一诊断来源。参见 [MDN：Long animation frame timing](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing)。

#### <u>项目最终把 FPS 和“数据提交频率”彻底分开</u>

旧逻辑曾经容易把 handleRealtimePacket 每秒执行几次误认为 FPS。

当前：

~~~text
rAF FPS
→ RafPerformanceMonitor 独立采集

submitRate
→ 页面实际提交了多少批数据
~~~

因此 batch 从 1 提高到 5 以后，即使提交次数下降，也不会再误判成 FPS 下降。

这是整个优化里非常重要的一次指标口径修正：

> **先把指标测对，再谈自适应控制。**

当前 rAF FPS 的真实实现如下：

```ts
// RenderPerformanceMonitor.ts
private readonly tick = (timestamp: number): void => {
  if (!this.running) return;
  if (this.windowStart === null) this.windowStart = timestamp;

  this.frameCount += 1;
  const elapsed = timestamp - this.windowStart;

  if (elapsed >= this.sampleWindowMs) {
    this.lastFps = this.frameCount * 1000 / elapsed;
    this.frameIntervalMs = elapsed / this.frameCount;
    this.baselineFps = Math.max(this.baselineFps, this.lastFps);
    this.onSample?.(this.snapshot());

    this.windowStart = timestamp;
    this.frameCount = 0;
  }

  this.handle = this.scheduler.request(this.tick);
};
```

这里没有读取 Queue，也没有读取 WebSocket 消费次数，因此即使当前没有新数据，它仍然持续反映浏览器 rAF 调度能力。

LoAF 的接入也直接位于页面运行链路中：

```ts
// dataVisualization.vue
this._loafDiagnostics = new LongFrameDiagnostics();

const supported = PerformanceObserver.supportedEntryTypes || [];
this.loafSupported = supported.includes("long-animation-frame");

if (this.loafSupported) {
  this.performanceObserver = new PerformanceObserver((list) => {
    list.getEntries().forEach((entry) =>
      this._loafDiagnostics.record(entry)
    );
  });

  this.performanceObserver.observe({
    type: "long-animation-frame",
    buffered: true,
  });
}
```

因此文档里的 `FPS` 和 `LoAF` 不是从实验脚本临时计算出来的两组脱节指标，而是当前页面本身已经内建的运行时诊断能力。

## 3. 受控实验逐步分离 K、N 与 H，形成二维和三维不同的性能模型

在测量口径正确以后，不直接修改代码，而是每次只改变一个关键变量，让实验结果决定下一步优化方向。

### 【Batch 实验首先证明二维受 K 影响明显，但三维不能只靠增加 batch】

#### <u>Batching 解决的是“重复支付固定更新成本”</u>

当输入固定 20 点/秒时：

~~~text
batch = 1
→ 最多 20 次页面更新

batch = 5
→ 可以把多个点合并进更少的页面更新
~~~

如果页面每次更新存在较大的 Fixed Cost（固定成本），增大 batch 就能减少 K。

项目进行了二维和三维的 batch sweep：

[batch-sweep-analysis.md](../reports/realtime-rendering/batch-sweep-analysis.md)

二维结果：

| batch | 消费 / 接收 | Pending | FPS 均值 |
| ---: | ---: | ---: | ---: |
| 1 | 414 / 1180 | 766 | 10.49 |
| 5 | 1055 / 1160 | 105 | 25.51 |
| 10 | 1180 / 1180 | 0 | 46.19 |
| 20 | 1180 / 1180 | 0 | 54.94 |

这说明二维中：

> **降低 K 确实有效，固定提交成本是主要组成之一。**

但是三维出现完全不同的结果：

| batch | 消费 / 接收 | Pending | FPS 均值 | LoAF P95 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 342 / 1160 | 818 | 9.07 | 249.5 ms |
| 5 | 860 / 1160 | 300 | 6.75 | 582.7 ms |
| 20 | 1140 / 1140 | 0 | 7.47 | 739.2 ms |

这里最重要的结论是：

> **Queue 清空不等于页面流畅。**

三维通过更大的 batch 把吞吐追平了，但单帧工作更重，FPS 反而下降，LoAF 尾部明显恶化。

所以三维不能继续把“加 batch”当成主优化方向。

---

### 【Rate 实验进一步证明三维的核心变量之一是 N，而不仅仅是 K】

为了判断三维是不是“每秒实际画的点太多”，项目继续降低实际输入量。

证据：

[rate-sweep-analysis.md](../reports/realtime-rendering/rate-sweep-analysis.md)

三维结果：

| rate | FPS 均值 | LoAF P95 | Cesium 回调单帧均值 |
| ---: | ---: | ---: | ---: |
| 1 | 44.08 | 93.2 ms | 13.7 ms |
| 2 | 34.33 | 84.3 ms | 17.3 ms |
| 5 | 16.18 | 192.1 ms | 35.5 ms |
| 10 | 9.62 | 421.6 ms | 57.5 ms |
| 20 | 7.47 | 739.2 ms | 134.6 ms |

在相同 batch 的交叉对照中，只降低 rate 就能获得数倍 FPS 改善。

因此结论从“每次更新太频繁”继续推进到“单位时间真正进入三维场景的数据量本身太大”。

也就是：

> 三维性能同时受 **K 和 N** 影响，其中 N 是非常强的变量。

这也解释了为什么项目需要两个控制旋钮：

~~~text
maxPerFrame
→ 控制客户端每次提交多少点
→ 主要调 K

maxPointsPerSecond
→ 控制当前连接每秒接收多少点
→ 直接调 N
~~~

---

### 【History 实验把问题从“实时输入”继续推进到 H：历史规模会改变新增一点的成本】

#### <u>历史规模不是只影响内存，还可能放大每次更新的计算量</u>

项目固定实时输入，只改变开始时已经存在的可视历史：

~~~text
0
200
500
1000
3000
5000
8000
~~~

证据：

[history-scale-analysis.md](../reports/realtime-rendering/history-scale-analysis.md)

二维平均 FPS 在 200～8000 点之间没有形成明显单调下降，但 LoAF 尾部持续恶化。

例如 LoAF P95：

~~~text
200 点   95.7 ms
1000 点 254.0 ms
3000 点 465.6 ms
8000 点 949.3 ms
~~~

这说明：

> **平均 FPS 稳定，不代表没有严重偶发卡顿。**

三维从 200 点以后出现更明确的规模退化：

~~~text
200 点   122.49 FPS
1000 点  114.32 FPS
3000 点   96.61 FPS
5000 点   66.05 FPS
8000 点   48.31 FPS
~~~

同时 Cesium 回调次数和累计耗时明显增加。

因此定位继续推进到：

> **历史规模 H 会放大三维场景成本，也会放大二维的尾部长帧风险。**

## 4. 优先降低 C 与 H：让一次实时更新只处理真正变化的部分

实验已经证明仅调整 batch 无法解决所有问题，因此下一步先削减单次更新成本 C，并阻止历史规模 H 持续放大一次更新的工作量。

### 【父组件：把大数组移出响应式系统，用“批次 + 版本号”驱动子组件】

**要解决的问题**：Vue 2 的响应式依赖 `Object.defineProperty` 对数据递归改写。如果把一个**持续增长**的地图点数组交给响应式系统（例如让子组件对它 `deep watch`），会同时放大两件事：

- 每次依赖收集都要**递归遍历整个数组**，历史越长，单次更新成本 `C` 越随历史规模 `H` 增长；
- 子组件监听到的是“完整数组”，即使只新增一个点，也等于**把整段历史重新处理一遍**。

也就是“新增少量数据”的代价被全量历史放大——这正是前面 `C`、`H` 两个变量恶化的源头之一。

**当前做法**：不再让大数组驱动更新，而是把它**排除在响应式系统之外**，只用“一个批次 + 一个版本号”显式触发。做法由三个动作组成。

**① 冻结外壳：让大数组不进入响应式系统。**

```ts
// dataVisualization.vue
// 冻结外壳阻止 Vue 2 对完整实时点数组递归观测；数组本身仍可追加。
realtimeMapStore: Object.freeze({ points: [] }),
```

Vue 2 在初始化观测时，遇到被 `Object.freeze` 的对象会直接跳过（`Object.isFrozen` 为真即 return），因此 `points` 不会被递归转成响应式属性——没有逐元素的 getter/setter，也就没有“每次更新全量依赖收集”。注意这是**浅冻结**：冻结的是 `{ points }` 外壳，`points` 数组本身仍可 `push`。

**② 原地追加，不产生中间数组。**

```ts
// utils/visualizationData.ts
export function appendRealtimeBatch<T extends object>(
  points: T[] | null | undefined,
  incoming: T[] | null | undefined,
  maxPoints = REALTIME_MAP_MAX_POINTS,
): T[] {
  const currentPoints = Array.isArray(points) ? points : [];
  if (Array.isArray(incoming)) {
    for (const point of incoming) {
      if (point && typeof point === "object") currentPoints.push(point);
    }
  }
  const limit = Math.floor(maxPoints);
  if (limit > 0 && currentPoints.length > limit) {
    currentPoints.splice(0, currentPoints.length - limit);
  }
  return currentPoints;
}
```

它直接在原数组上 `push`（不新建数组、不触发响应式），只在超过容量 `REALTIME_MAP_MAX_POINTS` 时从头部裁剪。成本与**新增点数**成正比，而不是与历史长度成正比。

**③ 用“批次 + 版本号”驱动子组件。** 父组件提交时只自增一个整数版本号，并只把本帧新增点交给子组件：

```ts
// dataVisualization.vue
realtimeMapStore: Object.freeze({ points: [] }),
realtimeBatch: [],
realtimeBatchId: 0,

...

const nextGasPoints = appendRealtimeTimeWindow(
  this.gasdata.data,
  result.data,
);

appendRealtimeBatch(this.realtimeMapStore.points, result.data);

this.gasdata = { ...result, data: nextGasPoints };
this.visualPointCount = this.realtimeMapStore.points.length;
this.realtimeBatch = result.data.slice(); // 本帧新增点（浅拷贝，避免与 store 共享引用）
this.realtimeBatchId += 1;                 // 唯一的触发信号
```

子组件不再 deep watch 完整 `mapList`，而是只监听这个版本号：

```ts
// PlanimetricMap.vue
mapList: { deep: false, handler(newVal) { if (this.searchType === 1) return; /* 历史兼容 */ } },

/** 只监听批次版本，不再深度遍历不断增长的完整 mapList。 */
realtimeBatchId() {
  if (this.searchType !== 1) return;
  if (this.$parent && this.$parent.mapType !== 1) return;
  this.drawRealtimeBatch(this.realtimeBatch);
},
```

`realtimeBatchId` 是 Number，比较是 O(1)，不涉及任何数组遍历；收到新批次后 `drawRealtimeBatch` 只绘制“末尾新增的这一段”（`startIndex = 总长度 − 批次长度`），不重画历史。于是链路从“整数组驱动”收敛为：

~~~text
realtimeBatchId changed
        ↓
读取 realtimeBatch
        ↓
只绘制这一批新增点
~~~

#### <u>它同时解决两个问题，并划清“数据”与“响应式 UI”的边界</u>

1. **更新成本不再随历史规模增长**：大数组被排除在响应式之外，触发信号是 O(1) 的版本号，而不是对全量数组的递归扫描；
2. **地图只处理新增批次**：`realtimeBatch` 只带本帧的点，绘制只发生在尾部区间，而不是“完整历史重新处理”。

由此得到一条更一般的边界：**完整历史数组只负责保存数据，`realtimeBatch + realtimeBatchId` 才负责驱动实时绘制**。Vue 只需要把真正驱动 UI 的少数状态保留为响应式——`visualPointCount`、`realtimeBatch`、`realtimeBatchId`、当前详情点、当前天气点；其余大量不会再次修改的遥测字段不必全部转成深层响应式属性：

> **业务数据可以很多，但不是每一个字段都必须成为响应式状态。**

**代价**：数组既然不再响应式，父组件就必须**手动**维护 `visualPointCount`（供界面展示）并自增 `realtimeBatchId`（通知子组件）。这套设计用“手动、O(1) 的显式触发”替换了“自动、随规模膨胀的深度响应式触发”，即从“**历史状态驱动更新**”改成“**增量事件驱动更新**”。此外，可视层的超窗淘汰（`evictOutsideHistoryWindow`）与数组容量裁剪（`REALTIME_MAP_MAX_POINTS`）互相独立，前者按时间约束绘制对象，后者只保护数组长度。

### 【二维地图从“对象不断增长 + 高频重复工作”改成增量 Scene 更新】

核心原则：**一次数据变化只触发与这次变化直接相关的 Scene 修改**。二维实时更新主要处理三件事——最新车辆位置、新增路线坐标、新增浓度点。

#### <u>每次只绘制新增区间</u>

新增批次只处理新增区间，不重画历史：

```ts
// PlanimetricMap.vue
drawRealtimeBatch(batch) {
  if (!Array.isArray(batch) || !batch.length) return;

  this.points = Array.isArray(this.mapList) ? this.mapList : [];
  this.evictOutsideHistoryWindow();

  const startIndex = Math.max(0, this.points.length - batch.length);
  const lastIndex = this.points.length - 1;

  for (let index = startIndex; index <= lastIndex; index++) {
    this.drawRealtimePoint(index, index === lastIndex);
  }

  this.index = lastIndex;
  this.dataForm = this.points[lastIndex];
}
```

`startIndex = 总长度 − 批次长度`，因此一次提交只遍历新增的这一段——降低的是**一次提交的遍历成本**。

#### <u>轨迹由大量两点 Feature 改成 256 点 Chunk</u>

**什么叫 256 点 Chunk**：一条轨迹在几何上是一条折线，但 OpenLayers 不会把它画成“一条无限长的 LineString”，而是切成若干**段（Chunk）**——每一段是一个独立的 `LineString` Feature，最多容纳 `ROUTE_CHUNK_MAX_POINTS = 256` 个连续坐标点。这里的“点”指轨迹上的采样点（车辆每一个上报位置）。

新增点时优先“接”到当前还在用的那一段：

- **当前段未满（点数 < 256）且与上一点首尾相接** → `appendCoordinate()` 把新坐标接到这段折线上，**复用同一个 Feature**；
- **当前段已满（≥ 256）或路径不连续** → `new LineString([previousCoordinate, currentCoordinate])` **另起一段**并 `addFeature`，避免画出一条错误的跨断点连线。

于是整条轨迹由 **≈ 总点数 / 256** 段长折线拼成，而不是“每两个点一条短线”。例如约 1 万个点时，旧写法会产生近 1 万个两点 Feature，分块后只需约 40 个 Feature——OpenLayers 每帧需要遍历与渲染的对象数量因此下降约两个数量级。

当前二维轨迹使用：

~~~text
ROUTE_CHUNK_MAX_POINTS = 256
~~~

新增点时：

~~~text
已有 Chunk 未满
→ appendCoordinate()

Chunk 已满
→ 新建下一段
~~~

源码：

[PlanimetricMap.vue](../QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)

这把大量独立短线对象收敛为少量长 Chunk，降低 OpenLayers 每轮需要管理的 Feature 数量。对应实现是 `drawRouteSegment`：

```ts
// PlanimetricMap.vue
const ROUTE_CHUNK_MAX_POINTS = 256;

drawRouteSegment(previous, current) {
  ...
  if (
    !this.routeChunkFeature ||
    this.routeChunkPointCount >= ROUTE_CHUNK_MAX_POINTS ||
    !continuous
  ) {
    this.routeChunkFeature = new Feature({
      geometry: new LineString([previousCoordinate, currentCoordinate]),
      color: "#12FF9B",
    });
    this.routeSource.addFeature(this.routeChunkFeature);
    this.routeChunkPointCount = 2;
  } else {
    this.routeChunkFeature.getGeometry()
      .appendCoordinate(currentCoordinate);
    this.routeChunkPointCount += 1;
  }
}
```

两者分别降低不同成本：只绘制新增区间降低**一次提交的遍历成本**，Chunk 复用降低 **Scene 对象数量**。

### 【三维地图的核心优化是消除“每帧动态计算”和“每次全量重建”】

#### <u>静态柱体不再使用持续求值的 CallbackProperty</u>

当前实时柱体**直接赋值** position、dimensions、material，而不是用会在每个 Cesium Frame 被持续求值的 `CallbackProperty`：

```ts
// StereoscopicMap.vue
const entity = this.viewer.entities.getById(entityId);
if (entity && entity.box) {
  entity.position = position;                  // 直接赋值
  entity.box.dimensions = dimensions;          // 直接赋值
  entity.box.material = new Cesium.ColorMaterialProperty(material);
}
```

这样已经静态的柱体属性不会在每个 Cesium Frame 中反复执行动态 Callback。它降低的是：

~~~text
H × 每帧动态属性求值
~~~

带来的场景成本。

源码：

[StereoscopicMap.vue](../QHZHC_Web/src/views/DataVisualization/components/StereoscopicMap.vue)

#### <u>三维轨迹改为 256 点分段增量维护</u>

**先说结论：改造前并不是增量，而是“每来一批就把整段历史轨迹重建一遍”。**

**改造前**：实时数据靠监听完整 `mapList` 触发，回调把**整个列表**交给 `updateRealtimeRoute`：

```ts
// StereoscopicMap.vue（改造前，节选）
mapList: {
  handler(newval) {
    this.index = newval.length - 1;
    this.prevData = newval[this.index - 1];
    this.nowBar(newval[this.index]);
    this.updateRealtimeRoute(newval);   // ← 传入的是完整历史 newval
  },
},

updateRealtimeRoute(points) {
  this.clearRealtimeRoute();            // 先移除全部 realtime-route-* 实体
  this.appendRealtimeRoute(points);     // 再按完整历史重新生成
  this.requestRender();
},
```

也就是说：每新增一批点，都会**先删光所有轨迹实体、再按完整历史重建一遍**。历史越长，这次重建越贵——这正是“新增 1 点 → O(H)”的来源。（`appendRealtimeRoute` 这个名字当时就有，但它被喂的是**全量列表**，所以整体仍是 O(H) 重建。）

**改造后**：不再监听完整 `mapList`，而是只监听批次版本号 `realtimeBatchId`，并**只把本帧新增批次**交给 `appendRealtimeRoute`：

```ts
// StereoscopicMap.vue（改造后）
/** 只监听批次版本，不再对完整历史做 deep watch。 */
realtimeBatchId() {
  this.drawRealtimeBatch(this.realtimeBatch);
},

drawRealtimeBatch(batch) {
  // ...
  this.appendRealtimeRoute(batch);   // ← 只传本帧新增点
  this.requestRender();
},
```

现在轨迹按：

~~~text
REALTIME_ROUTE_CHUNK_POINTS = 256
~~~

分段维护——新点只追加到**当前活动段**（≤256 点），段满才新建下一条 polyline：

~~~text
新增 1 点
→ 活动段未满：append position
→ 活动段已满：新建一条 polyline 实体
~~~

于是热点从：

~~~text
新增 1 点
→ O(H) 全量重建
~~~

收敛为接近：

~~~text
新增 1 点
→ O(1) 增量处理
~~~

**为什么“往 polyline 加坐标”本身不叫增量？** 成本取决于两件事：

1. **喂进去的输入范围**：喂“本帧批次”还是“完整历史”。喂全量，就会去动所有历史实体；
2. **单段长度是否封顶**：如果只维护一条无限长的 polyline，每次更新 `positions` 都要让 Cesium 重新求值一个长度 `H` 的几何，依然是 O(H)。所以必须有 `256` 这个上限，把“追加目标”限制成常数长度。

> 补充：即便现在，`state.activeEntity.polyline.positions = state.activePositions.slice()` 每次也会新建数组并让 Cesium 重新计算几何，但长度被 256 限死，因此是“相对历史 `H` 的 O(1)”，而不是绝对零成本。

**全量重建并没有被删除，只是不再走实时路径**：`updateRealtimeRoute`（clear + 全量 append）仍被重绘/历史快照复用——`redrawRealtimeWindow()` 与 `renderRealtimeSnapshot()` 会调用它整窗重画；实时帧则只用 `appendRealtimeRoute(batch)` 做增量追加。

轨迹的增量维护由一个长期存在的“活动段”状态机承担——`appendRealtimeRoute` 只向当前段追加 position，段满 256 点才新建 polyline：

```ts
// StereoscopicMap.vue
const REALTIME_ROUTE_CHUNK_POINTS = 256;

appendRealtimeRoute(points) {
  if (!this.realtimeRouteState) {
    this.realtimeRouteState = Object.preventExtensions({
      nextGroupIndex: 0,
      activeEntity: null,
      activePositions: [],
      lastPosition: null,
    });
  }

  const state = this.realtimeRouteState;

  for (const point of points) {
    const position = Cesium.Cartesian3.fromDegrees(
      Number(point.longitude),
      Number(point.latitude),
      REALTIME_ROUTE_HEIGHT,
    );

    if (!state.lastPosition) {
      state.lastPosition = position;
      continue;
    }

    if (
      !state.activeEntity ||
      state.activePositions.length >= REALTIME_ROUTE_CHUNK_POINTS
    ) {
      const positions = [state.lastPosition, position];
      state.activeEntity = this.viewer.entities.add({
        id: `realtime-route-${state.nextGroupIndex++}`,
        polyline: { positions, width: 5 },
      });
      state.activePositions = positions;
    } else {
      state.activePositions.push(position);
      state.activeEntity.polyline.positions =
        state.activePositions.slice();
    }

    state.lastPosition = position;
  }
}
```

这里最关键的不是 `256` 这个具体数字，而是**轨迹不再从完整历史重新生成，而是维护一个长期存在的增量状态机**。

#### <u>Cesium 默认进入按需渲染，而不是无变化也持续运行 Scene</u>

当前 Viewer：

Cesium 官方 Viewer 文档提供 requestRenderMode 和 maximumRenderTimeChange 用于显式渲染控制。参见 [CesiumJS Viewer](https://cesium.com/learn/cesiumjs/ref-doc/Viewer.html)。


二维地图会根据最新采样时间计算 cutoff，只删除超窗的浓度点 Feature：

```ts
// PlanimetricMap.vue
evictOutsideHistoryWindow() {
  const windowMs = Number(this.historyWindowMs) || 0;
  if (!windowMs || !this.pointSource) return 0;

  const points = Array.isArray(this.mapList) ? this.mapList : [];
  const latestTs = Date.parse(points[points.length - 1]?.time);
  const cutoff = latestTs - windowMs;

  const features = this.pointSource.getFeatures();
  let removed = 0;

  while (removed < features.length) {
    const feature = features[removed];
    const ts = Date.parse(feature?.get?.("data")?.time);
    if (!Number.isFinite(ts) || ts >= cutoff) break;

    this.pointSource.removeFeature(feature);
    removed += 1;
  }

  return removed;
}
```

这段代码同时说明当前边界：**淘汰的是 Scene 中的浓度点，不是父组件逻辑数组，也不是轨迹 Chunk**。

#### <u>当前边界：轨迹 Chunk 还没有按窗口淘汰</u>

二维和三维源码都明确：轨迹按 Chunk 保留，目前没有逐点时间信息，因此窗口淘汰只约束浓度点 / 柱体，不约束轨迹段。

这意味着：

~~~text
Point / Bar Object
已经有 History Window

Route Chunk
仍会随运行继续增长
~~~

因此“长期运行场景对象已经完全有界”目前还不能作为结论。

## 5. 再控制 K 与 N：从分帧批量消费升级到运行时自适应过载保护

当单次绘制已经尽量轻量化以后，再通过客户端批量控制 K，通过服务端订阅档位控制 N，最后由反馈控制器根据真实运行状态动态调整。

### 【第二类优化降低 K：FrameTelemetryQueue 把接收和绘制节奏彻底解耦】

当前 WebSocket 接收：

~~~text
message arrives
        ↓
enqueue()
~~~

不会直接要求页面立刻绘制。

真正的页面提交由：

~~~text
requestAnimationFrame
        ↓
flush()
        ↓
maxPerFrame
~~~

控制。

这形成 Producer–Consumer（生产者—消费者）模型。

当前 maxPerFrame 支持运行时热更新，因此网络连接不变、服务端不感知、Queue 不清空，就可以直接调整客户端消费批量。

热更新实现只有客户端本地状态变化：

```ts
// FrameTelemetryQueue.ts
setMaxPerFrame(value: number): void {
  const next = FrameTelemetryQueue.normalizeLimit(value);
  if (next === this.maxPerFrame) return;

  this.maxPerFrame = next;
  this.schedule();
}

private flush(): void {
  this.frameHandle = null;
  const startedAt = this.scheduler.now();
  const batch: TelemetryPoint[] = [];

  while (
    this.cursor < this.queue.length &&
    batch.length < this.maxPerFrame &&
    (
      batch.length === 0 ||
      this.scheduler.now() - startedAt < this.budgetMs
    )
  ) {
    const point = this.queue[this.cursor++];
    if (point) batch.push(point);
  }

  if (batch.length) {
    this.totalConsumed += batch.length;
    this.onFrame(batch);
  }
  ...
}
```

`batch.length === 0 || ...` 保证即使本帧取点预算已经耗尽，也至少消费一个点，避免 Queue 因预算判断永久空转。

- [frameTelemetryQueue.spec.js](../QHZHC_Web/tests/unit/frameTelemetryQueue.spec.js)
- [frameTelemetryQueueMetrics.spec.js](../QHZHC_Web/tests/unit/frameTelemetryQueueMetrics.spec.js)

已经覆盖 batch 归一化、Pending、热更新、oldestPendingMs、数据守恒、最低消费保证和受控吞吐。

### 【第三类优化降低 N：页面过载时减少真正进入可视化的数据量】

当前实时协议支持 maxPointsPerSecond。

合法档位：

~~~text
0 / 1 / 2 / 5 / 10 / 20

0 = 全部
~~~

它在 authenticate 消息中发送给服务端。

因此：

~~~text
maxPerFrame
控制客户端消费方式
        ↓
不需要重连

maxPointsPerSecond
控制服务端当前连接下发量
        ↓
需要重建连接使订阅参数生效
~~~

客户端修改输入档位的真实链路如下：

```ts
// realtimeClient.ts
socket.send(JSON.stringify({
  type: "authenticate",
  accessToken,
  protocolVersion: PROTOCOL_VERSION,
  robotId: ROBOT_ID,
  resumeFromBucketStartMs:
    this.latestBatchStartMs + SECOND_MS,
  maxPointsPerSecond: this.maxPointsPerSecond,
}));
```

当控制器或用户改变档位时：

```ts
private applyPointLimit(value: DeliveryPointLimit): void {
  if (
    !ALLOWED_POINT_LIMITS.includes(value) ||
    value === this.maxPointsPerSecond
  ) {
    return;
  }

  this.maxPointsPerSecond = value;

  if (
    this.socket &&
    this.socket.readyState < WebSocket.CLOSING
  ) {
    this.socket.close(
      REALTIME_CLOSE_CODE.PAGE_HIDDEN,
      "subscription changed",
    );
  }
}
```

这里之所以需要重建连接，是因为 `maxPointsPerSecond` 是 authenticate 阶段发送给服务端的订阅参数；而 `maxPerFrame` 完全是客户端 Queue 参数，所以两者不能复用同一种更新方式。

#### <u>降低 N 是过载保护，不是无成本优化</u>

降低订阅档位意味着当前实时可视链路主动减少展示点。

所以当前设计优先：

~~~text
先调 K
        ↓
如果 Queue 仍持续过载
并且单帧已经不能再安全加重
        ↓
再降低 N
~~~

这是用一部分可视采样密度换取页面实时可用性的保护策略，不能描述成“无损优化”。

### 【AdaptiveRenderController 把静态参数优化升级为反馈控制系统】

写死 batch 无法适配不同设备、刷新率、二维/三维差异、History Size、用户交互和输入变化，因此项目增加：

[AdaptiveRenderController.ts](../QHZHC_Web/src/views/DataVisualization/services/AdaptiveRenderController.ts)

它**不持有网络连接和 Timer**，只是每秒接收一个运行样本、返回一个决策，因此可以用确定性样本做 A/B 测试。下面按“输出 → 输入 → 决策”的顺序拆开它的算法。

#### <u>算法全貌：Observe → Evaluate → Act → Observe</u>

`AdaptiveRenderController` 本质上是一个离散的 Rule-based Feedback Controller（基于规则的反馈控制器），不是 PID。它没有连续的 P / I / D 误差项，而是在固定采样周期内根据 Queue、FPS 和 Render Cost 判断当前系统处于“健康、过载、超预算”中的哪一种状态，再选择离散动作。

完整闭环：

~~~text
Observe
读取一次运行样本
FPS / Baseline / Arrival / Pending / Queue Age / Render P95
        ↓
Evaluate
1. 当前帧预算是多少？
2. 追平输入和积压需要多大 batch？
3. Queue 是在增长还是缩小？
4. 当前渲染 P95 是否仍在预算内？
        ↓
Act
┌───────────────────────────────────────┐
│ Queue 过载 + Render 仍有余量          │
│ → 增大 batch，先提高客户端消费能力 K  │
├───────────────────────────────────────┤
│ Queue 过载 + Render 已超预算          │
│ → 不再增加 batch，退回安全批量         │
├───────────────────────────────────────┤
│ 持续过载 + batch 无法安全增加         │
│ → 降低输入 rate，减少 N               │
├───────────────────────────────────────┤
│ Queue 清空 + FPS / Render 持续健康     │
│ → 缓慢减 batch，并逐级恢复 rate        │
└───────────────────────────────────────┘
        ↓
Observe Again
下一轮继续根据真实结果反馈调整
~~~

所以控制器解决的不是“求一个固定最优 batch”，而是：

> **在设备能力、历史规模和输入负载持续变化的情况下，动态寻找“既能追上输入，又不突破单帧预算”的运行点。**

它控制两个不同层次的旋钮：

~~~text
第一层：batchSize
改变同样数据被分成多少次页面提交
主要调 K
通常不减少数据完整性

第二层：maxPointsPerSecond
改变真正进入当前可视链路的数据总量
主要调 N
会牺牲一部分可视采样密度
~~~

因此动作优先级必须是：

~~~text
先调 K
        ↓
只要单帧还有预算
就优先提高消费能力
        ↓
K 已经不能安全提高
并且持续过载
        ↓
再调 N
~~~

这也是整个控制算法最重要的设计取舍：**先改变“怎么消费”，最后才改变“消费多少数据”。**

#### <u>它只输出两个旋钮：每帧消费量 K 与输入档位 N</u>

- **`batchSize`（K）**：每帧从帧队列取多少点交给渲染层；
- **`requestedPointLimit`（N）**：是否把服务端订阅档位调低或恢复（`null` 表示不动）。

输入档位是一个有序阶梯：

~~~text
POINT_LIMIT_LADDER = [0, 20, 10, 5, 2, 1]
~~~

**越往右越省**（`0` 表示不限制、`1` 表示每秒最多 1 点）。所谓“降低输入”就是沿阶梯右移一格，“恢复”就是左移一格。

#### <u>第一步：把一次样本折算成几个判据</u>

控制器每秒拿到一个样本，包含 `actualFps / baselineFps`、`arrivalRate / consumeRate`、`pending / oldestPendingMs`、`renderP95Ms / frameIntervalMs`、`effectivePointLimit`。`evaluate()` 开头先把它们折算成判据：

```ts
// AdaptiveRenderController.ts（evaluate 开头）
const frameBudgetMs = Math.max(1, frameIntervalMs / 2);   // 单帧预算 = 帧间隔的一半
const actualFps = Math.max(1, sample.actualFps || sample.baselineFps || 1);

const requiredBatchSize = clamp(                          // 追平“到达 + 积压”所需的每帧点数
  Math.ceil(
    (Math.max(0, sample.arrivalRate) +
      Math.max(0, sample.pending) / this.catchUpWindowSeconds) / actualFps,
  ),
  this.minBatchSize,
  this.maxBatchSize,
);

const queueSlope = sample.pending - this.previousPending; // >0 表示积压在增长

const fpsHealthy =
  sample.baselineFps <= 0 || sample.actualFps >= sample.baselineFps * 0.9;

const renderWithinBudget =
  sample.renderP95Ms <= 0 || sample.renderP95Ms <= frameBudgetMs;

const overloaded =
  sample.oldestPendingMs > this.queueAgeLimitMs || queueSlope > 0;
```

各个判据的含义：

| 判据 | 含义 |
| --- | --- |
| `frameBudgetMs` | 单帧允许的渲染耗时上限，取帧间隔的一半（项目自己的保守预算，非浏览器标准阈值） |
| `requiredBatchSize` | 要在 `catchUpWindowSeconds`（默认 2s）内既跟上到达、又清空当前积压，每帧大约要消费多少点 |
| `queueSlope` | 与上一轮相比积压是变多还是变少 |
| `fpsHealthy` | 实测帧率是否达到基线的 90% |
| `renderWithinBudget` | 渲染耗时 P95 是否在单帧预算内 |
| `overloaded` | **队首等待超过 `queueAgeLimitMs`（默认 1s），或积压仍在增长** |
| `healthy` | `pending === 0 且 oldestPendingMs === 0 且 fpsHealthy 且 renderWithinBudget`（队列清空且帧率、渲染都健康） |

#### <u>第二步：先调 K（每帧消费量）</u>

K 的调整围绕一条“安全线” `safeBatchSize`——**曾经被证实能在预算内渲染的最大批量**。每轮先更新安全线，再据此决策：

```ts
// 预算内：把当前批量记为新的安全线
if (renderWithinBudget) this.safeBatchSize = Math.max(this.safeBatchSize, this.batchSize);
// 超预算：说明当前批量太大，把安全线下调到它以下
else this.safeBatchSize = Math.max(this.minBatchSize, Math.min(this.safeBatchSize, this.batchSize - 1));
```

然后按“过载 / 健康 / 中间态”三分支调整 K：

```ts
if (overloaded) {
  this.overloadWindows += 1;
  this.healthyWindows = 0;
  this.healthySinceMs = null;
  if (renderWithinBudget) {
    // 还有余量 → 加 K：向“安全线 + 1”试探，同时不低于 requiredBatchSize
    const probeCeiling = Math.min(this.maxBatchSize, this.safeBatchSize + 1);
    this.batchSize = Math.min(
      probeCeiling,
      Math.max(this.batchSize + 1, requiredBatchSize),
    );
    reason = "queue growing; increase batch";
  } else {
    // 已超预算 → 退回到安全线
    this.batchSize = Math.min(this.batchSize, this.safeBatchSize);
    reason = "render budget reached";
  }
} else if (healthy) {
  this.overloadWindows = 0;
  this.healthyWindows += 1;
  if (this.healthySinceMs === null) this.healthySinceMs = sample.nowMs;
  // 持续健康 → 缓慢减 K（每 healthyWindowsBeforeDecrease 次减 1），把余量还回去
  if (this.healthyWindows >= this.healthyWindowsBeforeDecrease && this.batchSize > this.minBatchSize) {
    this.batchSize -= 1;
    this.healthyWindows = 0;
    reason = "healthy; decrease batch slowly";
  }
} else {
  // 中间态：既不过载也不完全健康 → 保持不动，清空计数
  this.overloadWindows = 0;
  this.healthyWindows = 0;
  this.healthySinceMs = null;
}
```

一句话：**过载且有余量 → 试探性加 K；过载但已超预算 → 退回安全线；持续健康 → 缓慢减 K；其余保持。**

#### <u>第三步：只有当“持续过载且 K 已无法安全增大”才降 N</u>

降 N 是**最后手段**：先把 K 加到加不动为止，仍然持续过载，才请求降低输入档位。

```ts
const cannotIncreaseSafely =
  !renderWithinBudget || this.batchSize >= this.maxBatchSize;

if (
  this.overloadWindows >= this.overloadWindowsBeforeThrottle &&      // 连续 3 个过载窗口
  cannotIncreaseSafely &&                                            // K 已无法再安全增大
  sample.nowMs - this.lastPointLimitChangeAt >= this.throttleCooldownMs  // 距上次降档 ≥30s
) {
  requestedPointLimit = this.nextLowerPointLimit(sample.effectivePointLimit); // 沿阶梯右移一格
  if (requestedPointLimit !== null) {
    this.lastPointLimitChangeAt = sample.nowMs;
    this.overloadWindows = 0;
    reason = "sustained overload; lower input rate";
  }
}
```

#### <u>恢复同样保守：持续健康后才试探性升 N</u>

```ts
} else if (
  healthy &&
  this.healthySinceMs !== null &&
  sample.nowMs - this.healthySinceMs >= this.recoveryHealthyMs &&    // 持续健康 ≥60s
  sample.nowMs - this.lastPointLimitChangeAt >= this.throttleCooldownMs
) {
  requestedPointLimit = this.nextHigherPointLimit(
    sample.effectivePointLimit, this.desiredPointLimit,
  ); // 沿阶梯左移一格，逐级恢复到用户期望档位，不会一步跳满
  if (requestedPointLimit !== null) {
    this.lastPointLimitChangeAt = sample.nowMs;
    this.healthySinceMs = sample.nowMs;
    reason = "healthy; probe higher input rate";
  }
}
```

注意升档方向：`desiredPointLimit` 是用户期望的档位，`nextHigherPointLimit` 只允许**一次一级**朝它靠近，因此降档后不会立刻被拉回。

#### <u>整套防震荡参数</u>

| 参数 | 默认 | 作用 |
| --- | ---: | --- |
| `overloadWindowsBeforeThrottle` | 3 | 连续过载多少轮才考虑降 N |
| `healthyWindowsBeforeDecrease` | 5 | 连续健康多少轮才把 K 减 1 |
| `throttleCooldownMs` | 30000 | 两次改 N 之间的最小间隔 |
| `recoveryHealthyMs` | 60000 | 升 N 前需要持续健康多久 |
| `queueAgeLimitMs` | 1000 | 队首等待超过它即判过载 |
| `catchUpWindowSeconds` | 2 | `requiredBatchSize` 里清空积压的目标窗口 |

这些参数保证控制器**宁可慢、不可抖**：加 K 是连续试探，减 K 是每 5 轮才降 1，改 N 有 30s 冷却，升 N 还要先连续健康 60s。

#### <u>一轮具体计算：为什么会从 batch=5 试探到 6，而不是直接跳到 20</u>

假设某一轮采样得到：

~~~text
arrivalRate = 20 点/s
pending = 100 点
catchUpWindow = 2s
actualFps = 10

frameIntervalMs = 16ms
renderP95Ms = 5ms

当前 batch = 5
safeBatch = 5
~~~

第一步先算这一轮的 Frame Budget：

~~~text
frameBudget
= 16 / 2
= 8ms
~~~

因为：

~~~text
renderP95 = 5ms
<
frameBudget = 8ms
~~~

所以当前单帧仍有余量。

第二步计算理论 requiredBatch：

~~~text
每秒新输入
= 20

希望 2 秒追完 100 个积压：
100 / 2 = 50 点/s

目标消费能力：
20 + 50 = 70 点/s

当前只有 10 次 rAF 消费机会 / 秒：
70 / 10 = 7 点 / 帧

requiredBatch = 7
~~~

如果只看公式，似乎应该直接：

~~~text
batch 5 → 7
~~~

但控制器还存在 `safeBatchSize + 1` 的 Conservative Probe（保守探测）上限：

```ts
const probeCeiling = Math.min(
  this.maxBatchSize,
  this.safeBatchSize + 1,
);

this.batchSize = Math.min(
  probeCeiling,
  Math.max(this.batchSize + 1, requiredBatchSize),
);
```

当前：

~~~text
safeBatch = 5
probeCeiling = 6
requiredBatch = 7
~~~

最终：

~~~text
batch = min(6, 7)
      = 6
~~~

所以控制器不会因为积压突然从 5 跳到 7、20 或 50，而是先试探 `6`，下一轮重新观察真实 `renderP95 / FPS / Queue`。如果 `6` 仍在预算内，`safeBatch` 才会继续上移；如果 `6` 让渲染超预算，就立即停止探测。

这说明 `requiredBatchSize` 只是：

> **吞吐角度希望达到的 batch。**

而 `safeBatchSize` 是：

> **渲染预算允许达到的 batch。**

最终实际 batch 必须同时满足二者。

#### <u>为什么算法不能简单写成“FPS 低就减 batch，Queue 多就加 batch”</u>

如果只看 Queue：

~~~text
Queue ↑
→ batch ↑
~~~

那么三维场景可能出现：

~~~text
batch ↑
→ 单次 Cesium 更新更重
→ Frame Time ↑
→ FPS ↓
→ 每秒 flush 次数更少
→ Queue 反而继续 ↑
~~~

如果只看 FPS：

~~~text
FPS 低
→ batch ↓
~~~

又可能让客户端消费能力进一步低于 Arrival Rate，Queue 更快增长。

所以当前算法必须同时观察两个方向：

~~~text
Data Pressure
Queue / Queue Age / Arrival
        +
Frame Pressure
FPS / Render P95 / Frame Budget
~~~

只有两组信号结合，才能区分：

~~~text
“只是消费太慢，可以适当加 batch”
和
“单帧已经太重，必须停止加 batch甚至降低输入”
~~~

#### <u>从控制理论角度，它属于离散规则反馈控制，而不是 PID</u>

当前控制器具有几个典型特征：

| 特征 | 当前实现 |
| --- | --- |
| Feedback | 每轮使用上一轮运行结果继续决策 |
| Discrete Control | batch 和 rate 都是离散值 / 档位 |
| Threshold-based | 通过 Queue Age、Queue Slope、FPS、Render P95 判断状态 |
| Conservative Probe | batch 每次只允许突破已验证安全边界一级 |
| Hysteresis | 过载和健康都要求连续多个窗口才触发较大动作 |
| Cooldown | rate 调整之间至少间隔 30s |
| Slow Recovery | 持续健康 60s 才逐档恢复输入 |

它没有 PID 的连续误差积分与微分项，因此更准确的定义是：

> **Rule-based Adaptive Feedback Controller（基于规则的自适应反馈控制器）。**

选择这种方式的原因也很现实：当前系统的动作本身就是 `batch=1/2/3...` 与 `rate=20/10/5/2/1` 这样的离散控制，且页面性能关系明显非线性，用规则控制更容易解释、测试和设置安全边界。

因此控制器的真实优先级就是：**先提高消费能力 K，确认单帧仍有余量；再在持续过载时降低输入 N**。这与前文“先降 C / H，再控 K / N”的整体顺序一致。

## 6. 运行时观测把流畅度、吞吐、实时性和根因归因分开

### 【性能指标最终分成“流畅度、吞吐、实时性、归因”四层】

#### <u>第一层：流畅度</u>

~~~text
rAF FPS
baseline FPS
frameIntervalMs
LoAF P95 / Max
~~~

回答页面连续视觉更新是否正在恶化。

#### <u>第二层：吞吐</u>

~~~text
arrivalRate
consumeRate
pending
queueSlope
~~~

回答页面处理能力是否追得上数据输入。

#### <u>第三层：实时性</u>

~~~text
oldestPendingMs
~~~

回答最老的一条数据已经在 Queue 里等了多久。

#### <u>第四层：归因</u>

~~~text
renderP95Ms
LoAF stage
LoAF scripts
top invoker
forced layout
~~~

回答慢发生在页面提交、脚本执行还是渲染阶段。

#### <u>rAF FPS 的边界必须保留</u>

requestAnimationFrame 会在下一次 repaint 前安排 callback，调用频率通常接近显示刷新率，但后台标签页往往会暂停。它适合做同条件 A/B 和主线程调度能力观察，但不能直接等同于最终 Presented Frame 数量。参见 [MDN：requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。

例如 Queue 测试直接验证“输入能力大于消费能力时才应该积压”：

```js
// frameTelemetryQueueMetrics.spec.js
const runScenario = (maxPerFrame) => {
  const scheduler = new TimedScheduler();
  const queue = new FrameTelemetryQueue(
    jest.fn(),
    maxPerFrame,
    5,
    scheduler,
  );

  let sequence = 0;
  for (let second = 0; second < 5; second += 1) {
    queue.enqueue(
      Array.from({ length: 20 }, () => ({ sequence: sequence++ })),
    );

    for (let frame = 0; frame < 10; frame += 1) {
      scheduler.runFrame();
    }
  }

  return queue.pending();
};

expect(runScenario(1)).toBe(50);
expect(runScenario(2)).toBe(0);
```

自适应控制器测试则验证“单帧已经超预算时不能继续无脑加 batch”：

```js
// adaptiveRenderController.spec.js
const controller = new AdaptiveRenderController(5, 20);

const decision = controller.evaluate(sample({
  pending: 50,
  oldestPendingMs: 2_000,
  renderP95Ms: 12,
  frameIntervalMs: 16,
}));

expect(decision.frameBudgetMs).toBe(8);
expect(decision.batchSize).toBeLessThanOrEqual(4);
expect(decision.reason).toMatch(/budget/);
```

这类测试不是为了证明浏览器一定会达到某个 FPS，而是保证**控制规则本身不会在已超预算时继续把单帧工作推得更重**。

#### <u>当前历史窗口只淘汰浓度点和柱体，不淘汰轨迹 Chunk</u>

LoAF 对当前 Chrome 定位非常有价值，但兼容性仍有限，因此生产验收还需要 rAF / Frame Interval、Performance Trace、交互实测、Queue / Data Freshness 和目标设备 Soak 共同提供证据。参见 [MDN：Long animation frame timing](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing)。

## 8. 项目主线、证据入口与参考资料

### 【整个工作最终形成一条可复述的项目主线】

~~~text
发现持续实时数据下页面严重掉帧
        ↓
停止输入建立 Baseline
证明问题与持续更新强相关
        ↓
同时观察 FPS + Queue
确认 FPS 下降和积压形成正反馈
        ↓
Empty Render + LoAF
把瓶颈从 Queue 继续定位到真实绘制链路
        ↓
Batch Sweep
证明二维固定提交成本明显
并发现三维“Queue 清空但仍然卡”
        ↓
Rate Sweep
证明三维 N 是强瓶颈变量
        ↓
History Sweep
证明 H 会放大三维 Scene 成本
并放大二维尾部长帧
        ↓
降低 C / H
增量轨迹、去 deep watch、非响应式地图数据、
ECharts 合并更新、Cesium 按需渲染
        ↓
降低 K
FrameTelemetryQueue 批量消费
        ↓
过载时降低 N
maxPointsPerSecond
        ↓
建立 Feedback Control
根据 FPS / Queue / Render P95 自动调 batch / rate
        ↓
继续用 A/B + Unit Test + Smoke + Soak 验证
~~~

因此这个工作的技术价值不应该表述成：

> “用了 rAF 优化页面 FPS。”

更准确的答辩表达是：

> **我把实时数据页面建模成“数据生产—队列—按帧消费—页面提交—地图/图表绘制”的生产消费系统，先通过 rAF FPS、Queue 与 LoAF 建立可测量口径，再用 Batch、Rate、History 和 Empty Render 的受控实验分离更新频率、输入总量、单次成本与历史规模四类瓶颈。最终通过增量渲染、场景对象治理、批量消费和自适应限流形成闭环，让客户端能够根据实际设备和场景容量动态控制实时可视化负载。**
