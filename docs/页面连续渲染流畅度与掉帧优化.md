## 1. 工作目标与实时渲染主链

### 【实时可视化的核心目标不是“收到数据”，而是持续把最新数据稳定地呈现出来】

#### <u>实时链路存在“数据可靠到达”和“页面持续流畅”两条独立主线</u>

QHZHC 的实时页面同时承担：

- WebSocket 持续接收走航车遥测；
- 折线图更新气体与气象趋势；
- 二维 OpenLayers 地图更新车辆位置、浓度点和轨迹；
- 三维 Cesium 地图更新车辆、柱体和轨迹；
- 用户仍然需要拖拽、切换气体、切换二维/三维和查询历史数据。

因此系统不能只回答：

> 数据有没有通过 WebSocket 到达浏览器？

还必须继续回答：

> 数据到达以后，浏览器能不能持续按用户可接受的节奏把它画出来？

两条主线可以分开理解：

~~~text
Reliable Realtime Transport
WebSocket → Replay → Queue
解决：
数据能否连续到达
        ↓
Continuous Rendering
Queue → State → Map / Chart → Frame
解决：
到达的数据能否持续流畅呈现
~~~

如果第一条正常、第二条失效，会出现一种非常典型的“假实时”：

~~~text
服务端持续推送
WebSocket 也没有断
        ↓
前端处理不过来
        ↓
Queue 越积越多
        ↓
用户仍然看到画面变化
但看到的是越来越旧的数据
~~~

所以本项目把“页面流畅度”放在实时链路的核心位置，不只是为了视觉效果，而是为了同时保证：

- **Visual Continuity（视觉连续性）**：地图移动、轨迹增长和图表变化不能频繁冻结；
- **Data Freshness（数据新鲜度）**：页面不能因为积压越来越滞后；
- **Interaction Responsiveness（交互响应）**：持续推流时仍要能拖拽、点击和切换；
- **Long-running Stability（长期运行稳定性）**：页面运行时间增长后不能持续退化。

#### <u>当前实时数据从 WebSocket 到画面经过完整的生产消费链</u>

当前代码中的主链是：

~~~text
Server telemetry_second
        ↓
RealtimeClient.handleTelemetrySecond()
        ↓
FrameTelemetryQueue.enqueue()
        ↓
requestAnimationFrame
        ↓
FrameTelemetryQueue.flush()
        ↓
RealtimeClient.publishFrame()
        ↓
dataVisualization.handleRealtimePacket()
        ↓
┌────────────────────────────┐
│ Chart data                 │
│ Map realtime batch         │
│ Detail card                │
│ Weather latest point       │
└────────────────────────────┘
        ↓
Vue component update
        ↓
ECharts / OpenLayers / Cesium
        ↓
Browser Rendering
        ↓
Screen
~~~

源码入口：

- [realtimeClient.ts](../QHZHC_Web/src/views/DataVisualization/services/realtimeClient.ts)
- [FrameTelemetryQueue.ts](../QHZHC_Web/src/views/DataVisualization/services/FrameTelemetryQueue.ts)
- [dataVisualization.vue](../QHZHC_Web/src/views/DataVisualization/dataVisualization.vue)
- [Charts.vue](../QHZHC_Web/src/views/DataVisualization/components/Charts.vue)
- [PlanimetricMap.vue](../QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)
- [StereoscopicMap.vue](../QHZHC_Web/src/views/DataVisualization/components/StereoscopicMap.vue)

整个优化工作的关键，就是逐层判断：

> **到底是哪一步让页面无法继续按帧推进？**

关键链路在当前源码中不是概念图，而是下面这组真实调用：

```ts
// realtimeClient.ts
case "telemetry_second":
  this.handleTelemetrySecond(message);
  return;

private handleTelemetrySecond(message) {
  ...
  if (message.points.length > 0) {
    this.rateWindowReceived += message.points.length;
    this.totalReceived += message.points.length;
    this.frameQueue.enqueue(message.points);
    this.nextRenderPoint = this.frameQueue.peekNext();
  }
  ...
  this.frameQueue.resume();
}

private publishFrame(points: TelemetryPoint[]): void {
  if (!points.length) return;
  this.rateWindowConsumed += points.length;
  this.options.onPacket({
    code: 200,
    message: "ok",
    data: points.map(toLegacyPoint),
  });
}
```

这段代码把链路边界划得很清楚：WebSocket 收到的数据先进入 `FrameTelemetryQueue`，只有 Queue 在某个动画帧真正消费出一批点以后，才通过 `onPacket` 进入页面状态与地图/图表更新。因此 **网络接收频率和页面提交频率从这里开始被解耦**。

## 2. 从“页面卡”到可测量问题：基线、指标与诊断口径

这一阶段先回答：问题是否由持续数据更新触发、应该用什么指标描述，以及瓶颈究竟发生在 Queue、页面提交还是完整 Rendering Frame。

### 【初始问题不是简单的“FPS 低”，而是帧率下降与队列积压形成正反馈】

#### <u>第一阶段先建立无实时负载与持续负载的对照</u>

最早的现象是：停止持续数据更新后页面基本流畅；打开持续输入以后，二维和三维都会出现明显掉帧，并且随着运行继续出现积压。

当前保留的基线实验给出了更明确的数据。

在旧实现、20 点/秒输入、batch=1、约 60 秒的条件下：

| 指标 | 二维 | 三维 |
| --- | ---: | ---: |
| rAF FPS 均值 | 10.49 | 9.07 |
| FPS P5 | 4.19 | 3.95 |
| 接收 / 消费 | 1180 / 414 | 1160 / 342 |
| 结束 Pending | 766 | 818 |
| LoAF P95 | 239.4 ms | 249.5 ms |
| LoAF 最大 | 411 ms | 1032 ms |

证据：

- [二维 LoAF 实验](../reports/realtime-rendering/loaf-60s-verified/analysis.md)
- [三维 LoAF 实验](../reports/realtime-rendering/loaf-60s-3d-verified/analysis.md)

这里已经能够得到第一个关键结论：

~~~text
Arrival Rate
约 20 点/s
        >
实际 Consume Rate
二维约 6.9 点/s
三维约 5.7 点/s
~~~

所以 Pending 必然持续增加。

#### <u>FPS 下降和 Queue 增长会互相放大</u>

当前消费队列由 rAF 驱动：

~~~text
rAF 触发一次
        ↓
最多消费 maxPerFrame 个点
~~~

因此：

~~~text
FPS ↓
        ↓
每秒可用 flush 次数 ↓
        ↓
Consume Rate ↓
        ↓
Pending ↑
        ↓
数据等待更久
并可能让后续状态和场景更重
        ↓
FPS 继续下降
~~~

这不是单纯的“页面偶尔掉几帧”，而是一种可能持续恶化的 Performance Collapse（性能塌缩）。

这也是为什么项目后来同时监控 rAF FPS、arrivalRate、consumeRate、pending、oldestPendingMs 和 queueSlope，而不是只保留一个 FPS。

---

### 【性能定位先抽象为 N、K、C、H、B 五个变量，再设计实验逐个排除】

为了避免直接凭感觉修改代码，整个实时渲染问题可以抽象为五个变量：

| 变量 | 项目中的含义 |
| --- | --- |
| **N：Input Volume** | 单位时间真正进入页面可视链路的数据点数 |
| **K：Update Frequency** | 单位时间触发多少次页面状态 / 地图 / 图表提交 |
| **C：Cost Per Update** | 一次更新本身做多少计算、响应式处理和绘制工作 |
| **H：History / Scene Size** | 页面已经积累多少历史点、Feature、Entity 和轨迹对象 |
| **B：Frame Budget** | 当前设备、刷新率和场景能够提供多少帧预算 |

当前项目中的对应关系：

~~~text
N
→ maxPointsPerSecond
→ 服务端实际推给当前连接多少可视点

K
→ maxPerFrame / batch
→ 同一批数据被拆成多少次页面提交

C
→ Vue Commit
→ ECharts setOption
→ OpenLayers / Cesium 单次更新工作量

H
→ map points
→ Feature / Entity / Route Chunk
→ Chart Window

B
→ actualFps
→ baselineFps
→ frameIntervalMs
~~~

有了这个模型以后，定位问题就不再是“哪个函数看起来慢”，而是先判断：

> **到底应该减少 N、K、C、H 中哪一个，或者当前 B 本来就不足？**

---

### 【第一轮定位先证明瓶颈主要发生在真实绘制链路，而不是队列本身】

#### <u>FrameTelemetryQueue 只负责取点，不代表完整渲染预算</u>

当前队列位于：

[FrameTelemetryQueue.ts](../QHZHC_Web/src/views/DataVisualization/services/FrameTelemetryQueue.ts)

核心逻辑是：

~~~ts
while (
  cursor < queue.length &&
  batch.length < maxPerFrame &&
  (
    batch.length === 0 ||
    now() - startedAt < budgetMs
  )
) {
  batch.push(queue[cursor++]);
}

onFrame(batch);
~~~

这里的 budgetMs = 5 只包围从 Queue 中取出这一批数据，没有包住后面的 Vue 状态更新、Watcher / Props、ECharts、OpenLayers、Cesium 和浏览器绘制。

因此“每帧取点预算只有 5ms”不能被解释成“整个页面每帧只做 5ms 工作”。

#### <u>Empty Render 实验把 Queue 调度和真实绘制拆开</u>

当前 [dataVisualization.vue](../QHZHC_Web/src/views/DataVisualization/dataVisualization.vue) 保留 emptyRender 实验开关。

打开后：

~~~text
Queue 正常消费
        ↓
handleRealtimePacket 正常被调用
        ↓
不写入响应式状态
        ↓
Map / Chart 不更新
~~~

如果空渲染明显恢复，而真实渲染变差，就能够说明：

> Queue 和 rAF 调度不是主要瓶颈，真正成本在后续页面提交与绘制链路。

因此项目没有直接把问题归咎于 WebSocket 或 Queue，而是继续向 Vue、ECharts、OpenLayers、Cesium 方向排查。

---

### 【LoAF 把“页面卡”进一步定位到一整个动画帧，而不是只看 Long Task】

#### <u>rAF FPS 负责看到现象，LoAF 负责解释严重长帧</u>

当前项目使用两套独立机制。

第一套：

[RenderPerformanceMonitor.ts](../QHZHC_Web/src/views/DataVisualization/services/RenderPerformanceMonitor.ts)

通过独立 rAF 循环统计 actualFps、baselineFps 和 frameIntervalMs。

第二套：

[LongFrameDiagnostics.ts](../QHZHC_Web/src/views/DataVisualization/services/LongFrameDiagnostics.ts)

通过 PerformanceObserver 监听 long-animation-frame，并记录 duration、renderStart、styleAndLayoutStart、scripts、forcedStyleAndLayoutDuration、P95 / Max 以及最耗时脚本和 invoker。

MDN 将 LoAF 定义为延迟超过 50ms 的动画帧，并提供脚本和渲染阶段信息用于定位卡顿来源。LoAF 当前仍属于 Limited Availability / Experimental 能力，因此项目中保留 feature detection，不能把它作为唯一诊断来源。参见 [MDN：Long animation frame timing](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing)。

#### <u>项目最终把 FPS 和“数据提交频率”彻底分开</u>

旧逻辑曾经容易把 handleRealtimePacket 每秒执行几次误认为 FPS。

当前：

~~~text
rAF FPS
→ RafPerformanceMonitor 独立采集

submitRate
→ 页面实际提交了多少批数据
~~~

因此 batch 从 1 提高到 5 以后，即使提交次数下降，也不会再误判成 FPS 下降。

这是整个优化里非常重要的一次指标口径修正：

> **先把指标测对，再谈自适应控制。**

当前 rAF FPS 的真实实现如下：

```ts
// RenderPerformanceMonitor.ts
private readonly tick = (timestamp: number): void => {
  if (!this.running) return;
  if (this.windowStart === null) this.windowStart = timestamp;

  this.frameCount += 1;
  const elapsed = timestamp - this.windowStart;

  if (elapsed >= this.sampleWindowMs) {
    this.lastFps = this.frameCount * 1000 / elapsed;
    this.frameIntervalMs = elapsed / this.frameCount;
    this.baselineFps = Math.max(this.baselineFps, this.lastFps);
    this.onSample?.(this.snapshot());

    this.windowStart = timestamp;
    this.frameCount = 0;
  }

  this.handle = this.scheduler.request(this.tick);
};
```

这里没有读取 Queue，也没有读取 WebSocket 消费次数，因此即使当前没有新数据，它仍然持续反映浏览器 rAF 调度能力。

LoAF 的接入也直接位于页面运行链路中：

```ts
// dataVisualization.vue
this._loafDiagnostics = new LongFrameDiagnostics();

const supported = PerformanceObserver.supportedEntryTypes || [];
this.loafSupported = supported.includes("long-animation-frame");

if (this.loafSupported) {
  this.performanceObserver = new PerformanceObserver((list) => {
    list.getEntries().forEach((entry) =>
      this._loafDiagnostics.record(entry)
    );
  });

  this.performanceObserver.observe({
    type: "long-animation-frame",
    buffered: true,
  });
}
```

因此文档里的 `FPS` 和 `LoAF` 不是从实验脚本临时计算出来的两组脱节指标，而是当前页面本身已经内建的运行时诊断能力。

## 3. 受控实验逐步分离 K、N 与 H，形成二维和三维不同的性能模型

在测量口径正确以后，不直接修改代码，而是每次只改变一个关键变量，让实验结果决定下一步优化方向。

### 【Batch 实验首先证明二维受 K 影响明显，但三维不能只靠增加 batch】

#### <u>Batching 解决的是“重复支付固定更新成本”</u>

当输入固定 20 点/秒时：

~~~text
batch = 1
→ 最多 20 次页面更新

batch = 5
→ 可以把多个点合并进更少的页面更新
~~~

如果页面每次更新存在较大的 Fixed Cost（固定成本），增大 batch 就能减少 K。

项目进行了二维和三维的 batch sweep：

[batch-sweep-analysis.md](../reports/realtime-rendering/batch-sweep-analysis.md)

二维结果：

| batch | 消费 / 接收 | Pending | FPS 均值 |
| ---: | ---: | ---: | ---: |
| 1 | 414 / 1180 | 766 | 10.49 |
| 5 | 1055 / 1160 | 105 | 25.51 |
| 10 | 1180 / 1180 | 0 | 46.19 |
| 20 | 1180 / 1180 | 0 | 54.94 |

这说明二维中：

> **降低 K 确实有效，固定提交成本是主要组成之一。**

但是三维出现完全不同的结果：

| batch | 消费 / 接收 | Pending | FPS 均值 | LoAF P95 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 342 / 1160 | 818 | 9.07 | 249.5 ms |
| 5 | 860 / 1160 | 300 | 6.75 | 582.7 ms |
| 20 | 1140 / 1140 | 0 | 7.47 | 739.2 ms |

这里最重要的结论是：

> **Queue 清空不等于页面流畅。**

三维通过更大的 batch 把吞吐追平了，但单帧工作更重，FPS 反而下降，LoAF 尾部明显恶化。

所以三维不能继续把“加 batch”当成主优化方向。

---

### 【Rate 实验进一步证明三维的核心变量之一是 N，而不仅仅是 K】

为了判断三维是不是“每秒实际画的点太多”，项目继续降低实际输入量。

证据：

[rate-sweep-analysis.md](../reports/realtime-rendering/rate-sweep-analysis.md)

三维结果：

| rate | FPS 均值 | LoAF P95 | Cesium 回调单帧均值 |
| ---: | ---: | ---: | ---: |
| 1 | 44.08 | 93.2 ms | 13.7 ms |
| 2 | 34.33 | 84.3 ms | 17.3 ms |
| 5 | 16.18 | 192.1 ms | 35.5 ms |
| 10 | 9.62 | 421.6 ms | 57.5 ms |
| 20 | 7.47 | 739.2 ms | 134.6 ms |

在相同 batch 的交叉对照中，只降低 rate 就能获得数倍 FPS 改善。

因此结论从“每次更新太频繁”继续推进到“单位时间真正进入三维场景的数据量本身太大”。

也就是：

> 三维性能同时受 **K 和 N** 影响，其中 N 是非常强的变量。

这也解释了为什么项目需要两个控制旋钮：

~~~text
maxPerFrame
→ 控制客户端每次提交多少点
→ 主要调 K

maxPointsPerSecond
→ 控制当前连接每秒接收多少点
→ 直接调 N
~~~

---

### 【History 实验把问题从“实时输入”继续推进到 H：历史规模会改变新增一点的成本】

#### <u>历史规模不是只影响内存，还可能放大每次更新的计算量</u>

项目固定实时输入，只改变开始时已经存在的可视历史：

~~~text
0
200
500
1000
3000
5000
8000
~~~

证据：

[history-scale-analysis.md](../reports/realtime-rendering/history-scale-analysis.md)

二维平均 FPS 在 200～8000 点之间没有形成明显单调下降，但 LoAF 尾部持续恶化。

例如 LoAF P95：

~~~text
200 点   95.7 ms
1000 点 254.0 ms
3000 点 465.6 ms
8000 点 949.3 ms
~~~

这说明：

> **平均 FPS 稳定，不代表没有严重偶发卡顿。**

三维从 200 点以后出现更明确的规模退化：

~~~text
200 点   122.49 FPS
1000 点  114.32 FPS
3000 点   96.61 FPS
5000 点   66.05 FPS
8000 点   48.31 FPS
~~~

同时 Cesium 回调次数和累计耗时明显增加。

因此定位继续推进到：

> **历史规模 H 会放大三维场景成本，也会放大二维的尾部长帧风险。**

---

## 4. 优先降低 C 与 H：让一次实时更新只处理真正变化的部分

实验已经证明仅调整 batch 无法解决所有问题，因此下一步先削减单次更新成本 C，并阻止历史规模 H 持续放大一次更新的工作量。

### 【第一类正式优化先降低 C 和 H：让新增数据只处理新增部分】

#### <u>Vue 实时数据不再依赖不断增长数组的 deep watch</u>

当前父组件维护 realtimeMapStore、realtimeBatch 和 realtimeBatchId，其中 realtimeMapStore 使用冻结外壳保存实时点。

源码：

[dataVisualization.vue](../QHZHC_Web/src/views/DataVisualization/dataVisualization.vue)

地图子组件实时模式不再 deep watch 完整 mapList，而是：

~~~text
realtimeBatchId changed
        ↓
读取 realtimeBatch
        ↓
只绘制这一批新增点
~~~

对应：

- [PlanimetricMap.vue](../QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)
- [StereoscopicMap.vue](../QHZHC_Web/src/views/DataVisualization/components/StereoscopicMap.vue)

这解决两个问题：

1. 历史数组越长，Vue 不再每次都递归扫描全部点；
2. 地图拿到的是“新增批次”，而不是“完整历史重新处理”。

#### <u>地图数据和响应式 UI 数据拆开</u>

实时地图点存放在冻结外壳中，Vue 不需要把每一个不会再次修改的遥测字段全部转成深层响应式属性。

真正需要驱动 UI 的只保留 visualPointCount、realtimeBatch、realtimeBatchId、当前详情点和当前天气点。

这体现的是：

> **业务数据可以很多，但不是每一个字段都必须成为响应式状态。**

当前父组件真正提交实时批次的代码如下：

```ts
// dataVisualization.vue
realtimeMapStore: Object.freeze({ points: [] }),
realtimeBatch: [],
realtimeBatchId: 0,

...

const nextGasPoints = appendRealtimeTimeWindow(
  this.gasdata.data,
  result.data,
);

appendRealtimeBatch(this.realtimeMapStore.points, result.data);

this.gasdata = { ...result, data: nextGasPoints };
this.visualPointCount = this.realtimeMapStore.points.length;
this.realtimeBatch = result.data.slice();
this.realtimeBatchId += 1;
```

而地图子组件不再深度监听完整历史数组：

```ts
// PlanimetricMap.vue
mapList: {
  deep: false,
  handler(newVal) {
    if (this.searchType === 1) return;
    ... // 只保留历史查询兼容逻辑
  },
},

realtimeBatchId() {
  if (this.searchType !== 1) return;
  if (this.$parent && this.$parent.mapType !== 1) return;
  this.drawRealtimeBatch(this.realtimeBatch);
},
```

也就是说，**完整历史数组负责保存数据，`realtimeBatch + realtimeBatchId` 才负责驱动实时绘制**。这正是从“历史状态驱动更新”改成“增量事件驱动更新”的关键边界。

### 【二维地图从“对象不断增长 + 高频重复工作”改成增量 Scene 更新】

#### <u>轨迹由大量两点 Feature 改成 256 点 Chunk</u>

当前二维轨迹使用：

~~~text
ROUTE_CHUNK_MAX_POINTS = 256
~~~

新增点时：

~~~text
已有 Chunk 未满
→ appendCoordinate()

Chunk 已满
→ 新建下一段
~~~

源码：

[PlanimetricMap.vue](../QHZHC_Web/src/views/DataVisualization/components/PlanimetricMap.vue)

这把大量独立短线对象收敛为少量长 Chunk，降低 OpenLayers 每轮需要管理的 Feature 数量。

当前二维新增批次只处理新增区间：

```ts
// PlanimetricMap.vue
drawRealtimeBatch(batch) {
  if (!Array.isArray(batch) || !batch.length) return;

  this.points = Array.isArray(this.mapList) ? this.mapList : [];
  this.evictOutsideHistoryWindow();

  const startIndex = Math.max(0, this.points.length - batch.length);
  const lastIndex = this.points.length - 1;

  for (let index = startIndex; index <= lastIndex; index++) {
    this.drawRealtimePoint(index, index === lastIndex);
  }

  this.index = lastIndex;
  this.dataForm = this.points[lastIndex];
}
```

轨迹也不是每两个点永远新建一条线：

```ts
// PlanimetricMap.vue
const ROUTE_CHUNK_MAX_POINTS = 256;

drawRouteSegment(previous, current) {
  ...
  if (
    !this.routeChunkFeature ||
    this.routeChunkPointCount >= ROUTE_CHUNK_MAX_POINTS ||
    !continuous
  ) {
    this.routeChunkFeature = new Feature({
      geometry: new LineString([previousCoordinate, currentCoordinate]),
      color: "#12FF9B",
    });
    this.routeSource.addFeature(this.routeChunkFeature);
    this.routeChunkPointCount = 2;
  } else {
    this.routeChunkFeature.getGeometry()
      .appendCoordinate(currentCoordinate);
    this.routeChunkPointCount += 1;
  }
}
```

前一段解决“这一批只画新增点”，后一段解决“新增轨迹尽量复用当前 LineString”。两者分别降低一次提交的遍历成本和 Scene 对象数量。

#### <u>实时更新只处理与当前点直接有关的工作</u>

当前二维实时更新主要处理最新车辆位置、新增路线坐标和新增浓度点。

核心原则是：

> **一次数据变化只触发与这次变化直接相关的 Scene 修改。**

### 【三维地图的核心优化是消除“每帧动态计算”和“每次全量重建”】

#### <u>静态柱体不再使用持续求值的 CallbackProperty</u>

当前实时柱体直接更新 position、dimensions、material。

源码：

[StereoscopicMap.vue](../QHZHC_Web/src/views/DataVisualization/components/StereoscopicMap.vue)

不会让已经静态的柱体属性在每个 Cesium Frame 中持续执行动态 Callback。

这降低的是：

~~~text
H × 每帧动态属性求值
~~~

带来的场景成本。

#### <u>三维轨迹改为 256 点分段增量维护</u>

当前：

~~~text
REALTIME_ROUTE_CHUNK_POINTS = 256
~~~

轨迹只向当前活动段追加 position，不再每来一个点就重新构建完整历史轨迹。

热点从：

~~~text
新增 1 点
→ O(H) 全量重建
~~~

收敛为接近：

~~~text
新增 1 点
→ O(1) 增量处理
~~~

#### <u>Cesium 默认进入按需渲染，而不是无变化也持续运行 Scene</u>

当前 Viewer：

~~~text
shouldAnimate = false
requestRenderMode = true
maximumRenderTimeChange = Infinity
~~~

只有状态真正变化时主动 requestRender。

历史轨迹播放需要 Clock 时，再临时打开动画驱动，播放完成以后恢复按需渲染。

Cesium 官方 Viewer 文档提供 requestRenderMode 和 maximumRenderTimeChange 用于显式渲染控制。参见 [CesiumJS Viewer](https://cesium.com/learn/cesiumjs/ref-doc/Viewer.html)。

当前 Viewer 初始化直接体现了这个取舍：

```ts
// StereoscopicMap.vue
this.viewer = new Cesium.Viewer("cesiumContainer", {
  scene3DOnly: true,
  shouldAnimate: false,
  requestRenderMode: true,
  ...
});

this.viewer.clock.shouldAnimate = false;
this.viewer.scene.maximumRenderTimeChange = Infinity;
```

实时轨迹则通过活动 Chunk 增量追加：

```ts
// StereoscopicMap.vue
const REALTIME_ROUTE_CHUNK_POINTS = 256;

appendRealtimeRoute(points) {
  if (!this.realtimeRouteState) {
    this.realtimeRouteState = Object.preventExtensions({
      nextGroupIndex: 0,
      activeEntity: null,
      activePositions: [],
      lastPosition: null,
    });
  }

  const state = this.realtimeRouteState;

  for (const point of points) {
    const position = Cesium.Cartesian3.fromDegrees(
      Number(point.longitude),
      Number(point.latitude),
      REALTIME_ROUTE_HEIGHT,
    );

    if (!state.lastPosition) {
      state.lastPosition = position;
      continue;
    }

    if (
      !state.activeEntity ||
      state.activePositions.length >= REALTIME_ROUTE_CHUNK_POINTS
    ) {
      const positions = [state.lastPosition, position];
      state.activeEntity = this.viewer.entities.add({
        id: `realtime-route-${state.nextGroupIndex++}`,
        polyline: { positions, width: 5 },
      });
      state.activePositions = positions;
    } else {
      state.activePositions.push(position);
      state.activeEntity.polyline.positions =
        state.activePositions.slice();
    }

    state.lastPosition = position;
  }
}
```

这里最关键的不是 `256` 这个具体数字，而是**轨迹不再从完整历史重新生成，而是维护一个长期存在的增量状态机**。

## 5. 再控制 K 与 N：从分帧批量消费升级到运行时自适应过载保护

当单次绘制已经尽量轻量化以后，再通过客户端批量控制 K，通过服务端订阅档位控制 N，最后由反馈控制器根据真实运行状态动态调整。

### 【第二类优化降低 K：FrameTelemetryQueue 把接收和绘制节奏彻底解耦】

当前 WebSocket 接收：

~~~text
message arrives
        ↓
enqueue()
~~~

不会直接要求页面立刻绘制。

真正的页面提交由：

~~~text
requestAnimationFrame
        ↓
flush()
        ↓
maxPerFrame
~~~

控制。

这形成 Producer–Consumer（生产者—消费者）模型。

当前 maxPerFrame 支持运行时热更新，因此网络连接不变、服务端不感知、Queue 不清空，就可以直接调整客户端消费批量。

对应测试：

- [frameTelemetryQueue.spec.js](../QHZHC_Web/tests/unit/frameTelemetryQueue.spec.js)
- [frameTelemetryQueueMetrics.spec.js](../QHZHC_Web/tests/unit/frameTelemetryQueueMetrics.spec.js)

已经覆盖 batch 归一化、Pending、热更新、oldestPendingMs、数据守恒、最低消费保证和受控吞吐。

---

### 【第三类优化降低 N：页面过载时减少真正进入可视化的数据量】

当前实时协议支持 maxPointsPerSecond。

合法档位：

~~~text
0 / 1 / 2 / 5 / 10 / 20

0 = 全部
~~~

它在 authenticate 消息中发送给服务端。

因此：

~~~text
maxPerFrame
控制客户端消费方式
        ↓
不需要重连

maxPointsPerSecond
控制服务端当前连接下发量
        ↓
需要重建连接使订阅参数生效
~~~

#### <u>降低 N 是过载保护，不是无成本优化</u>

降低订阅档位意味着当前实时可视链路主动减少展示点。

所以当前设计优先：

~~~text
先调 K
        ↓
如果 Queue 仍持续过载
并且单帧已经不能再安全加重
        ↓
再降低 N
~~~

这是用一部分可视采样密度换取页面实时可用性的保护策略，不能描述成“无损优化”。

---

### 【AdaptiveRenderController 把静态参数优化升级为反馈控制系统】

写死 batch 无法适配不同设备、刷新率、二维/三维差异、History Size、用户交互和输入变化。

所以项目增加：

[AdaptiveRenderController.ts](../QHZHC_Web/src/views/DataVisualization/services/AdaptiveRenderController.ts)

它不持有网络连接和 Timer，只根据一次运行样本做一次决策。

#### <u>控制器每轮观察五类信号</u>

~~~text
actualFps
baselineFps
arrivalRate / consumeRate
pending / oldestPendingMs
renderP95Ms
frameIntervalMs
~~~

当前项目定义：

~~~text
frameBudgetMs
=
frameIntervalMs / 2
~~~

这是项目自己的保守控制预算，不是浏览器标准阈值。

同时估算 requiredBatchSize，用于回答：

> 按当前实际可用 FPS，要在目标时间内追平输入和积压，每帧大概要消费多少点。

#### <u>控制器先调 batch，batch 到安全边界后才调 rate</u>

当前逻辑可以压缩为：

~~~text
Queue Growing
+
Render Within Budget
        ↓
Increase Batch

Queue Growing
+
Render Budget Reached
        ↓
Do Not Increase Batch

Sustained Overload
+
Cannot Increase Safely
        ↓
Lower Input Rate

Queue Empty
+
FPS Healthy
+
Render Healthy
        ↓
Decrease Batch Slowly

Sustained Healthy
        ↓
Probe Higher Input Rate
~~~

并通过连续窗口、Cooldown 和慢恢复避免控制参数频繁震荡。

对应测试：

[adaptiveRenderController.spec.js](../QHZHC_Web/tests/unit/adaptiveRenderController.spec.js)

## 6. 运行时观测把流畅度、吞吐、实时性和根因归因分开

### 【性能指标最终分成“流畅度、吞吐、实时性、归因”四层】

#### <u>第一层：流畅度</u>

~~~text
rAF FPS
baseline FPS
frameIntervalMs
LoAF P95 / Max
~~~

回答页面连续视觉更新是否正在恶化。

#### <u>第二层：吞吐</u>

~~~text
arrivalRate
consumeRate
pending
queueSlope
~~~

回答页面处理能力是否追得上数据输入。

#### <u>第三层：实时性</u>

~~~text
oldestPendingMs
~~~

回答最老的一条数据已经在 Queue 里等了多久。

#### <u>第四层：归因</u>

~~~text
renderP95Ms
LoAF stage
LoAF scripts
top invoker
forced layout
~~~

回答慢发生在页面提交、脚本执行还是渲染阶段。

#### <u>rAF FPS 的边界必须保留</u>

requestAnimationFrame 会在下一次 repaint 前安排 callback，调用频率通常接近显示刷新率，但后台标签页往往会暂停。它适合做同条件 A/B 和主线程调度能力观察，但不能直接等同于最终 Presented Frame 数量。参见 [MDN：requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)。

ECharts 合并更新、Cesium 按需渲染
        ↓
降低 K
FrameTelemetryQueue 批量消费
        ↓
过载时降低 N
maxPointsPerSecond
        ↓
建立 Feedback Control
根据 FPS / Queue / Render P95 自动调 batch / rate
        ↓
继续用 A/B + Unit Test + Smoke + Soak 验证
~~~

因此这个工作的技术价值不应该表述成：

> “用了 rAF 优化页面 FPS。”

更准确的答辩表达是：

> **我把实时数据页面建模成“数据生产—队列—按帧消费—页面提交—地图/图表绘制”的生产消费系统，先通过 rAF FPS、Queue 与 LoAF 建立可测量口径，再用 Batch、Rate、History 和 Empty Render 的受控实验分离更新频率、输入总量、单次成本与历史规模四类瓶颈。最终通过增量渲染、场景对象治理、批量消费和自适应限流形成闭环，让客户端能够根据实际设备和场景容量动态控制实时可视化负载。**
