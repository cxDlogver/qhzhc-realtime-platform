## 1. 项目先从主线程时间如何被实时任务竞争开始

### 【实时可视化页面为什么首先是主线程调度问题】

#### <u>页面同时存在数据输入、状态更新、图形绘制和定时控制</u>

当前数据可视化页面并不是只有一条 JavaScript 逻辑。

运行期间同时存在：

~~~text
WebSocket message event
        ↓
实时数据校验与入队

requestAnimationFrame
        ↓
FrameTelemetryQueue 消费

Vue State Update
        ↓
组件更新 / nextTick

ECharts / OpenLayers / Cesium
        ↓
图形场景更新

setInterval
        ↓
Heartbeat / Watchdog / Stats

setTimeout
        ↓
Reconnect / Chart Coalescing

PerformanceObserver
        ↓
Long Animation Frame 诊断
~~~

这些机制的共同约束是：

> **它们最终不能让 Window Main Thread 长时间持续被某一段 JavaScript 或页面更新占满。**

否则即使 WebSocket 连接正常，仍然可能出现：

~~~text
Message Event 延迟
Timer 延迟
rAF 延迟
点击 / 拖拽延迟
页面掉帧
Queue 积压
~~~

所以任务调度文档关心的不是“哪一个 API 更快”，而是：

> **哪类工作应该进入哪一种调度边界，以及什么时候必须把执行权还给浏览器。**

## 2. 数据从 WebSocket Event 进入 rAF，再经过 Vue 更新到达画面

这一阶段沿一条真实数据流解释 Event Task、rAF 和 Framework Scheduling 如何依次衔接，而不是把三个 API 分开记忆。

### 【WebSocket Message Event 只负责把数据送入应用】

#### <u>网络事件进入页面以后仍然需要 Main Thread 执行 JavaScript 回调</u>

当前连接注册 Message Event：

~~~ts
// realtimeClient.ts
socket.onmessage = (event) => {
  if (this.socket !== socket || this.stopped) return;

  this.lastSeenAt = Date.now();

  let message;
  try {
    message = JSON.parse(event.data);
  } catch {
    this.options.onStatus("invalid-packet");
    return;
  }

  this.handleServerMessage(message);
};
~~~

浏览器可以在 JavaScript 主线程之外推进网络 I/O，但真正执行页面的 message event handler 时，仍然要进入页面 Event Loop 的 JavaScript 执行流程。

因此如果 onmessage 里直接：

~~~text
解析
→ Vue State
→ ECharts
→ OpenLayers
→ Cesium
~~~

那么：

~~~text
Network Arrival Rate
≈
View Commit Rate
~~~

数据到达越快，主线程越容易被高频页面更新占满。

#### <u>当前代码把 Message Event 与 Visual Commit 解耦</u>

实际处理遥测时：

~~~ts
// realtimeClient.ts
if (message.points.length > 0) {
  this.rateWindowReceived += message.points.length;
  this.totalReceived += message.points.length;

  this.frameQueue.enqueue(message.points);
  this.nextRenderPoint =
    this.frameQueue.peekNext();
}

this.frameQueue.resume();
~~~

这一步只负责：

~~~text
Message Event
        ↓
Validate / Normalize
        ↓
FrameTelemetryQueue
~~~

并没有要求：

~~~text
收到多少条
就立刻画多少次
~~~

所以这里建立了第一个任务边界：

> **网络事件负责产生数据，视觉调度负责决定什么时候把数据交给页面。**

---

### 【requestAnimationFrame 把数据消费移动到 Rendering Scheduling】

#### <u>FrameTelemetryQueue 通过 rAF 请求下一次视觉更新前的消费机会</u>

当前 Queue 抽象：

~~~ts
// FrameTelemetryQueue.ts
const browserFrameScheduler = {
  request: (callback) =>
    window.requestAnimationFrame(callback),

  cancel: (handle) =>
    window.cancelAnimationFrame(handle),

  now: () => performance.now(),
};
~~~

当 Queue 有数据时：

~~~ts
private schedule(): void {
  if (
    this.paused ||
    this.frameHandle !== null ||
    this.cursor >= this.queue.length
  ) {
    return;
  }

  this.frameHandle =
    this.scheduler.request(() => this.flush());
}
~~~

所以：

~~~text
enqueue
↓
只注册一个待执行 rAF
↓
浏览器到达合适 Rendering Opportunity
↓
flush
↓
取一批数据
↓
onFrame
↓
页面提交
~~~

而不是：

~~~text
enqueue
↓
同步立即渲染
~~~

#### <u>同一时间只允许存在一个待执行 rAF</u>

判断：

~~~ts
this.frameHandle !== null
~~~

非常重要。

它意味着：

~~~text
一秒内即使连续 enqueue 20 次
        ↓
不会注册 20 个独立 rAF
        ↓
已有 rAF 等待时只继续积累 Queue
~~~

因此输入 Burst 不会直接变成相同数量的动画帧回调。

#### <u>rAF 只改变执行时机，不自动减少 flush 之后的工作量</u>

真正的消费：

~~~ts
private flush(): void {
  this.frameHandle = null;

  const startedAt = this.scheduler.now();
  const batch = [];

  while (
    this.cursor < this.queue.length &&
    batch.length < this.maxPerFrame &&
    (
      batch.length === 0 ||
      this.scheduler.now() - startedAt <
        this.budgetMs
    )
  ) {
    const point =
      this.queue[this.cursor++];

    if (point) {
      batch.push(point);
    }
  }

  if (batch.length) {
    this.totalConsumed += batch.length;
    this.onFrame(batch);
  }

  if (this.cursor < this.queue.length) {
    this.schedule();
  }
}
~~~

这里的 budgetMs 只限制 Queue 取数循环。

它没有包住：

~~~text
onFrame
↓
Vue State Commit
↓
ECharts / Map
↓
Style / Layout / Rendering
~~~

所以：

> **rAF 解决的是“什么时候开始本次视觉提交”，不是“本次提交一定能在帧预算内结束”。**

这也是为什么项目还需要 Frame Time、LoAF 和 Render P95。

---

### 【Vue nextTick 是 Framework Scheduling 边界】

当前前端使用 Vue 2.6.14。

#### <u>状态更新以后通过 nextTick 等待 Vue Update Queue Flush</u>

例如历史窗口修改后：

~~~ts
// dataVisualization.vue
changeRealtimeHistoryWindow() {
  this.$nextTick(() => {
    this.evictOutsideHistoryWindow();
    this.refreshStats();
  });
}
~~~

这里注释已经说明原因：

~~~text
父组件更新 prop
        ↓
子组件 prop 不会在当前同步语句里立即完成刷新
        ↓
等待 Vue 完成本轮异步更新
        ↓
nextTick callback
        ↓
再读取新的窗口值
~~~

所以 nextTick 解决的是：

> **Framework State → Component / DOM Patch 的更新顺序问题。**

#### <u>nextTick 之后仍不能直接声称“用户已经看到新画面”</u>

初始化实时窗口以后：

~~~ts
this.$nextTick(() => {
  this.redrawRealtimeWindow();
});
~~~

这说明：

~~~text
先让 Vue 把本轮状态和组件更新推进完成
        ↓
再让 Map 使用新状态重画
~~~

但是：

~~~text
Vue nextTick callback
≠
浏览器 Presented Frame
~~~

因为后面还可能存在：

~~~text
Map JavaScript
Style / Layout
Paint
Raster
Composite
~~~

因此项目性能指标需要区分：

~~~text
State Commit
Framework Flush
Rendering Opportunity
Actual Frame
~~~

不能用 nextTick 代替 FPS 或 Paint 指标。

## 3. Timer 与 async-await 分别承担时间策略和异步流程恢复

### 【Timer 负责未来任务而不是精确视觉帧】

#### <u>ECharts 使用 setTimeout 做 Coalescing，而不是做 FPS</u>

当前图表实时更新：

~~~ts
// Charts.vue
scheduleUpdateOptions() {
  if (this.searchType !== 1) {
    this.updateOptions();
    return;
  }

  if (this.chartUpdateTimer !== null) {
    return;
  }

  this.chartUpdateTimer =
    setTimeout(() => {
      this.chartUpdateTimer = null;
      this.updateOptions();
    }, 120);
}
~~~

这里的目的不是：

~~~text
每 120ms 准确渲染一次
~~~

而是：

~~~text
第一次数据变化
↓
注册未来一次 Task
↓
120ms 窗口内其他变化
不再继续注册 Timer
↓
最终合并成一次 updateOptions
~~~

也就是 Coalescing（合并）。

如果 Main Thread 此时很忙：

~~~text
120ms
只是最早满足的时间条件

callback
可能更晚才真正执行
~~~

所以它适合降低 ECharts Update Frequency，不适合测量真正的 Frame Rate。

#### <u>Heartbeat 与 Watchdog 使用 setInterval 是周期检查，不是精确定时</u>

当前：

~~~ts
// realtimeClient.ts
this.heartbeatTimer =
  window.setInterval(() => {
    if (
      !this.socket ||
      this.socket.readyState !== WebSocket.OPEN
    ) {
      return;
    }

    if (
      Date.now() - this.lastSeenAt >
      this.heartbeatIntervalMs * 3
    ) {
      this.socket.close(
        REALTIME_CLOSE_CODE.HEARTBEAT_TIMEOUT,
        "heartbeat timeout",
      );
      return;
    }

    const now = Date.now();

    this.send({
      type: "ping",
      nonce: String(now),
      sentAt: now,
    });
  }, this.heartbeatIntervalMs);
~~~

这里真正关心的是：

~~~text
距离上次收到消息
是否已经超过阈值
~~~

而不是假设：

~~~text
setInterval 8000
→ callback 必定每 8000ms 精确执行
~~~

所以使用 Date.now() 再计算真实时间差，是正确的防御方式。

#### <u>重连 setTimeout 只表达“至少等这么久以后再尝试”</u>

当前指数退避：

~~~ts
const ceiling =
  Math.min(
    15_000,
    500 * 2 ** Math.min(this.attempt, 6),
  );

const delay =
  Math.max(
    250,
    Math.round(ceiling * this.random()),
  );

this.reconnectTimer =
  window.setTimeout(() => {
    this.reconnectTimer = null;
    this.connect();
  }, delay);
~~~

这里 delay 表示：

> **不要早于该时间再次重连。**

Main Thread 如果被长任务占用，实际 connect 可以更晚执行，这不会破坏退避语义。

---

### 【async-await 改变异步控制流而不是线程模型】

当前连接关闭后 Token 恢复：

~~~ts
private async handleClose(
  socket: WebSocket,
  event: CloseEvent,
): Promise<void> {
  ...

  try {
    await this.refreshAccessToken();

    if (!this.stopped) {
      this.attempt = 0;
      this.connect();
    }
  } catch (_error) {
    this.stopped = true;
    this.options.onStatus("error");
    await this.onAuthenticationFailure();
  }
}
~~~

这里：

~~~text
await refreshAccessToken
~~~

意味着当前 async 函数暂停后续执行，等待 Promise 完成。

但不能理解成：

~~~text
await
→ 开一个新线程
~~~

真正关系是：

~~~text
当前 JavaScript 返回
        ↓
异步 HTTP / Promise 在外部继续推进
        ↓
Promise settle
        ↓
Continuation 通过 Promise / Microtask 机制继续
~~~

所以 async / await 解决的是：

> **异步流程怎样表达和恢复。**

而 Worker 才是把可执行 JavaScript 工作放到另一个 Worker Agent 的机制。

## 4. 独立 rAF、Render P95 与 LoAF 共同证明主线程是否按时让出

### 【独立 rAF Monitor 测量真实调度机会】

#### <u>FPS 监控不能绑定 onPacket</u>

当前 RafPerformanceMonitor：

~~~ts
// RenderPerformanceMonitor.ts
private readonly tick =
  (timestamp: number): void => {
    if (!this.running) {
      return;
    }

    if (this.windowStart === null) {
      this.windowStart = timestamp;
    }

    this.frameCount += 1;

    const elapsed =
      timestamp - this.windowStart;

    if (elapsed >= this.sampleWindowMs) {
      this.lastFps =
        this.frameCount * 1000 / elapsed;

      this.frameIntervalMs =
        elapsed / this.frameCount;

      this.baselineFps =
        Math.max(
          this.baselineFps,
          this.lastFps,
        );

      this.onSample?.(this.snapshot());

      this.windowStart = timestamp;
      this.frameCount = 0;
    }

    this.handle =
      this.scheduler.request(this.tick);
  };
~~~

这个循环与：

~~~text
WebSocket 有没有新数据
Queue 有没有消费
页面提交了几次
~~~

都没有直接绑定。

因此它测的是：

> **当前页面还能够获得多少 rAF 调度机会。**

而业务 Submit Rate 单独统计。

这解决了一个典型错误：

~~~text
batch 增大
→ 每秒 onPacket 次数变少
→ 错误地认为 FPS 变低
~~~

---

### 【Long Task 与 Long Animation Frame 诊断长时间占用】

requestAnimationFrame 本身不能保证流畅。

如果某次回调以及后续页面更新非常重：

~~~text
rAF callback
↓
Vue
↓
OpenLayers / Cesium
↓
100ms
~~~

那么：

~~~text
虽然使用了 rAF
仍然会错过多个 Rendering Opportunity
~~~

当前页面监听 Long Animation Frame：

~~~ts
this.performanceObserver =
  new PerformanceObserver((list) => {
    list.getEntries().forEach(
      (entry) =>
        this._loafDiagnostics.record(entry),
    );
  });

this.performanceObserver.observe({
  type: "long-animation-frame",
  buffered: true,
});
~~~

所以诊断链是：

~~~text
rAF FPS
→ 看连续调度机会是否下降

Render P95
→ 看业务提交是否变重

LoAF
→ 看严重长帧发生在哪里
~~~

完整的掉帧与 N / K / C / H / B 根因分析继续阅读：

[页面连续渲染流畅度与掉帧优化](./页面连续渲染流畅度与掉帧优化.md)

## 5. Worker 只在纯 CPU 热点成立时进入下一层设计

### 【当前项目暂不把实时链路直接迁到 Worker】

#### <u>当前主要热点位于 Framework 与 Map / Chart Commit</u>

当前核心视觉更新最终必须调用：

~~~text
Vue State
ECharts
OpenLayers
Cesium
~~~

这些页面 API 大量依赖 Window / DOM / 当前图形上下文。

即使把：

~~~text
JSON Parse
坐标转换
部分采样计算
~~~

移入 Worker，

后续：

~~~text
Vue Commit
Map Entity / Feature Update
Chart setOption
~~~

仍然要回到主页面执行。

因此当前优先优化的是：

~~~text
减少 C
→ 增量绘制 / 少做重复工作

控制 H
→ 历史窗口 / Chunk

控制 K
→ rAF Queue / Batch

控制 N
→ 输入档位
~~~

而不是直接引入 Worker。

#### <u>Worker 更适合后续出现纯 CPU 热点时再引入</u>

如果未来 Profile 证明热点变成：

- 大批量空间计算；
- 数据聚合；
- 大规模采样；
- 数据解析；
- 与 DOM 无关的算法；

则可以继续评估：

~~~text
Main Thread
  ↓ postMessage
Worker
  ↓ CPU Work
Result
  ↓
Main Thread Commit
~~~

但 Worker 的判断依据应该来自 Profile，而不是“页面卡所以一定上 Worker”。

## 6. 项目最终形成四类调度语义和一条完整运行链

### 【四类调度语义不能互相替换】

| 项目机制 | 当前 API | 真正目的 | 不应该替换成什么 |
| --- | --- | --- | --- |
| Promise Continuation | async / await | 等异步结果后继续流程 | 不等于 Worker |
| Framework Flush | Vue nextTick | 等 Vue 本轮更新完成 | 不等于 Paint |
| Visual Scheduling | requestAnimationFrame | 下一次视觉更新前消费 / 更新 | 不等于精确 Timer |
| Future Task | setTimeout / setInterval | 延迟、重试、合并、周期检查 | 不等于 Frame Scheduler |

可以形成一张项目决策表：

~~~text
我要等待异步结果
→ Promise / await

我要等待 Vue 状态真正进入组件更新
→ nextTick

我要把视觉工作和屏幕更新机会对齐
→ requestAnimationFrame

我要晚一点再尝试 / 合并一段时间内的事件
→ setTimeout

我要做周期健康检查
→ setInterval + 实际时间差判断

我要处理纯 CPU 重计算
→ 先 Profile，再判断 Worker
~~~

---

### 【一次遥测消息从 Event Loop 一路到屏幕】

~~~text
Network Process / WebSocket I/O
        ↓
Message Event
        ↓
Window Event Loop 执行 onmessage
        ↓
handleServerMessage
        ↓
FrameTelemetryQueue.enqueue
        ↓
当前 Task 结束
        ↓
等待合适 Rendering Opportunity
        ↓
requestAnimationFrame callback
        ↓
FrameTelemetryQueue.flush
        ↓
publishFrame / onPacket
        ↓
Vue State Change
        ↓
Vue Update Queue
        ↓
Component Watch / DOM Patch
        ↓
Map / Chart JavaScript
        ↓
Style / Layout / Paint / Composite
        ↓
Presented Frame
~~~

与此同时存在独立旁路：

~~~text
Timer Task
→ Heartbeat / Watchdog / Chart Coalescing / Reconnect

Promise Microtask
→ async / await continuation

PerformanceObserver
→ Long Frame Diagnosis
~~~

这张图解释了为什么当前问题不能只用：

~~~text
宏任务
→ 微任务
~~~

两句话概括。

真实页面是：

> **网络事件、框架更新、视觉调度、定时任务和渲染流水线共同竞争有限的执行与帧预算。**

## 7. 设计价值与面试答辩从“调度边界”解释

### 【按任务语义选择调度边界而不是滥用 rAF】

当前项目可以总结为四个设计判断。

#### <u>网络输入与视觉更新必须解耦</u>

~~~text
WebSocket Message
→ Queue

Queue
→ rAF
→ View
~~~

避免 Network Arrival Rate 直接控制 Render Frequency。

#### <u>Timer 用于时间策略，rAF 用于视觉策略</u>

~~~text
Heartbeat / Reconnect / Coalesce
→ Timer

Visual Batch / FPS Sampling
→ rAF
~~~

避免用 setInterval 模拟帧率，也避免把 rAF 当通用异步工具。

#### <u>Framework nextTick 解决状态一致性，不负责证明 Paint</u>

~~~text
State Change
→ nextTick
→ Framework Update 已推进

但：
是否真正画到屏幕
→ 继续由 Browser Rendering 决定
~~~

#### <u>重任务首先减少和拆分，再考虑 Worker</u>

当前已经通过：

~~~text
Incremental Update
Batch
History Window
On-demand Render
~~~

减少主线程工作。

只有剩余热点确实属于可脱离 DOM 的 CPU-heavy Work 时，Worker 才进入下一层设计。

---

### 【面试与答辩从调度边界解释实现】

可以这样回答：

> 这个实时页面一开始的问题不是 WebSocket 收不到数据，而是网络输入节奏直接推动页面绘制，导致主线程不断执行 Vue、ECharts 和地图更新。后来我把网络 Event 和视觉更新拆成两个调度边界：WebSocket message handler 只负责校验和入 Queue，真正的可视数据提交由 requestAnimationFrame 驱动的 FrameTelemetryQueue 按帧批量消费。图表的高频更新再通过 setTimeout 合并，Heartbeat 和 Watchdog 用 setInterval 做周期检查，Vue nextTick 只负责等待框架 Update Flush，不把它当成 Paint 完成。这样不同 API 都按照自己的调度语义使用。性能定位时再通过独立 rAF FPS、Render P95 和 LoAF 判断主线程是不是被单次更新占用过久；如果未来出现与 DOM 无关的纯 CPU 热点，再考虑 Worker，而不是一开始就把所有问题归因到单线程。
