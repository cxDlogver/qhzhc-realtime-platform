# 01 实时前端系统中的背压与自适应调度

> 本文梳理实时前端系统中的通用知识、设计思想和工程规范。
> QHZHC 只作为贯穿示例，用来解释这些原则如何落地；项目变量、文件名和局部实现不会被当作知识点本身。

## 一、实时渲染首先是生产者与消费者的速率匹配问题

实时页面的本质不是“不断收到 WebSocket 数据”，而是一个持续运行的 Producer-Consumer（生产者—消费者）系统。

~~~text
生产者持续产生数据
        ↓
传输
        ↓
浏览器接收
        ↓
缓冲
        ↓
消费者处理
        ↓
状态更新 / 图表 / 地图 / Canvas / WebGL
~~~

只要上游和下游的平均速率不同，就会出现三种状态：

~~~text
消费速率 > 输入速率
→ 系统有余量，短暂积压可以被消化

消费速率 ≈ 输入速率
→ 系统处于临界区，一次 GC、长任务或复杂重绘就可能造成积压

消费速率 < 输入速率
→ 队列持续增长，数据越来越旧，内存和主线程压力继续增加
~~~

因此实时性能优化不能直接从“把 FPS 提高”开始，而应该先判断：输入是否过快、消费是否过慢、慢在传输还是渲染，以及问题是瞬时抖动还是长期容量不足。

### 项目示例：QHZHC

QHZHC 的实时页面会持续接收走航数据，并同时更新折线图、二维地图和三维地图。项目通过记录输入速率、消费速率和待处理数据量，把“页面卡顿”转化为一个可测量的生产消费问题。

这里值得复用的是分析方法：

~~~text
先测输入
再测消费
再观察积压
最后决定是扩消费、限输入还是优化单次渲染
~~~

### 答辩关注点

如果被问“为什么实时页面越跑越卡”，不能只回答“数据量大”。更完整的回答是：数据量只是现象，需要继续判断是生产消费失衡，还是单次渲染成本随着历史数据增长。

## 二、背压解决的是下游处理不过来时系统如何自我保护

Backpressure（背压）的核心不是简单限流，而是：当下游能力不足时，把压力反馈给上游或调度层，避免系统无限积压。

没有背压时，系统很容易形成恶化循环：

~~~text
短暂处理不过来
        ↓
缓冲区增长
        ↓
数据等待时间增加
        ↓
内存和 GC 压力增加
        ↓
消费能力进一步下降
        ↓
积压继续扩大
~~~

实时前端中的背压通常至少分三层：

| 层次 | 典型压力 | 常见处理方式 |
| --- | --- | --- |
| 传输层 | 发送缓冲增长、网络发不出去 | 暂停发送、断开慢连接、限制发送量 |
| 应用缓冲层 | 数据已到浏览器但消费不及 | 队列、批处理、合并、降采样 |
| 渲染层 | 单次 UI 更新过重 | 分帧、增量更新、虚拟化、对象复用 |

这三层不能混为一谈。网络没有积压，不代表页面没有积压；页面队列为空，也不代表地图绘制足够快。

### 项目示例：QHZHC

QHZHC 服务端会检查 WebSocket 的发送缓冲，浏览器端则维护独立的待渲染队列。因此项目实际同时处理“网络发送慢消费者”和“页面渲染慢消费者”。

这个实践说明：背压不是一个统一开关，而是应该按系统层次分别设计。

### 工程规范

不要用一个“系统是否卡顿”的总指标覆盖全部问题。应分别观测传输压力、缓冲压力和渲染压力，这样才能知道应该限网络输入、提高本地消费，还是优化渲染算法。

## 三、接收与渲染解耦是实时前端的第一条调度原则

一种常见但脆弱的实现是：收到一条消息，就立即更新状态和地图。

它隐含了一个错误假设：

~~~text
网络到包节奏
=
浏览器适合渲染的节奏
~~~

实际上网络事件和浏览器绘制属于两套调度系统。网络可以在很短时间内突发到达大量数据，但主线程和绘制窗口始终有限。

更稳定的结构是：

~~~text
接收层
只负责接收和轻量预处理
        ↓
缓冲层
暂存待处理数据
        ↓
调度层
决定什么时候、一次处理多少
        ↓
渲染层
完成真正的 UI 更新
~~~

这体现的是 Decoupling（解耦）：上游负责生产，下游按照自身可承受的节奏消费，中间通过缓冲区隔离突发流量。

队列的价值也不只是“存数据”，而是建立一个可控制的调度边界。有了这个边界，系统才能进一步做批处理、优先级、降采样、分帧和自适应调节。

### 项目示例：QHZHC

QHZHC 没有让实时消息直接驱动地图逐点更新，而是先进入客户端缓冲，再由帧调度逐批提交给页面。

这个实践真正体现的是“接收节奏与渲染节奏解耦”，而不是某个具体队列类的使用。

### 工程规范

实时接收回调应尽量少计算、少同步副作用、不执行大规模 DOM 或地图更新，并尽快返回事件循环。重计算可以进一步拆到 Worker，真正 UI 提交则交给渲染调度层。

## 四、requestAnimationFrame 是渲染调度入口，不是性能保证

requestAnimationFrame（请求动画帧，简称 rAF）会在浏览器下一次重绘前执行回调，因此适合组织连续视觉更新。

它解决的是“什么时候开始下一批与画面有关的工作”，不解决“这一批工作本身是不是太重”。

~~~text
使用 rAF
≠
自动稳定 60 FPS
~~~

如果一次回调及后续状态更新耗时 50 ms 或 80 ms，浏览器仍然会出现明显掉帧。

以 60 Hz 显示器为例，一帧理论间隔约 16.7 ms，但这段时间不全部属于业务 JavaScript。浏览器还要执行其他脚本、样式计算、布局、绘制和合成，所以业务处理通常需要更保守的时间预算。

官方资料：

- MDN requestAnimationFrame：https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
- MDN Page Visibility API：https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API

### 项目示例：QHZHC

QHZHC 使用 rAF 驱动客户端缓冲逐帧消费，并在页面隐藏时暂停实时渲染工作。

这个实践对应两条通用原则：rAF 用于对齐浏览器帧节奏；页面生命周期变化时，调度器必须能够暂停和恢复。

### 答辩关注点

如果被问“用了 rAF 为什么 FPS 还是低”，应回答：rAF 只是提供下一次帧调度机会，单次 JavaScript、状态更新或地图绘制超过帧预算时仍然会掉帧。

## 五、分帧处理的核心是限制单次主线程占用

Time Slicing（时间切片）表示把一大段工作拆到多个调度窗口中执行。

~~~text
一次处理 100 项
→ 一个长任务

拆分为多帧
→ 每帧处理一部分
→ 主线程获得更多让出机会
~~~

总业务工作量可能没有减少，但用户事件有机会执行，浏览器也有机会完成绘制。

分帧通常需要同时考虑两类预算：

~~~text
数量预算
+
时间预算
~~~

只限制数量无法应对不同任务成本差异；只限制时间又可能在轻任务场景下一次取出过多数据。因此更稳健的方案是同时约束“一次最多处理多少”和“本轮最多占用多久”。

此外必须保证 Forward Progress（前向进展）：即使预算很紧，也不能连续多帧一条数据都无法处理，否则会发生饥饿。

### 项目示例：QHZHC

QHZHC 的帧队列同时约束单帧处理数量和本轮取数据的时间，并保证每次调度至少能够推进一个数据项。

这里体现的通用规则是：限制单次工作量，但不能因为限制过严让队列永远无法前进。

### 工程规范

一个完整的分帧调度器还需要明确暂停是否保留数据、恢复从哪里继续、销毁是否清空缓冲、页面隐藏时如何处理，以及旧回调是否可能在任务取消后继续执行。这些属于生命周期设计，而不只是性能参数调优。
---

## 六、批处理优化的是提交次数和固定开销

Batching（批处理）的价值，不只是“单次处理更多数据”，而是减少重复提交。

很多实时页面每次更新都要支付固定成本，例如：

~~~text
状态对象创建
响应式通知
组件更新调度
图表更新入口
地图更新入口
任务切换
~~~

如果每个数据项都单独提交，这些固定成本会被重复支付。将多个小更新合并为一次较大的更新，可以摊薄这部分开销。

因此批处理优化的是：

~~~text
相同数据总量
通过更少的提交次数完成
~~~

但批次不能无限增大。批次太大时，队列虽然可以迅速清空，却可能制造一个更长的主线程任务。

所以批处理需要同时约束：

~~~text
吞吐量
和
单次提交成本
~~~

### 项目示例：QHZHC

QHZHC 在实时页面中允许根据运行状态调整每帧提交批量。批量增大时，页面提交次数会下降，积压更容易被消化；但如果单次提交开始变重，就不能继续无上限扩大批次。

这个实践说明：批处理的目标不是“越大越好”，而是在吞吐和单帧成本之间寻找平衡点。

### 答辩关注点

如果被问“总数据量没变，为什么批量处理反而更快”，应解释：数据量没有减少，但固定提交开销被摊薄，消费吞吐提高了；同时还必须强调批量过大会造成长帧。

---

## 七、自适应调度本质上是一个反馈控制系统

固定参数适合稳定负载，但实时页面的运行环境通常不断变化，包括网络输入、历史数据规模、机器性能、地图复杂度和浏览器当前负载。

因此更通用的方案是 Feedback Control（反馈控制）：

~~~text
观察当前状态
        ↓
判断是否偏离目标
        ↓
调整控制参数
        ↓
再次观察结果
~~~

一个完整控制环需要三部分。

### 【被观察量】

例如：

- 输入速率；
- 消费速率；
- 队列长度；
- 最老数据等待时间；
- 页面提交耗时；
- FPS；
- 长帧数量。

### 【控制量】

通常分成两类：

~~~text
本地消费能力
→ 一次处理多少、多久处理一次

上游输入压力
→ 一秒允许进入多少、是否降采样
~~~

### 【控制目标】

实时系统往往同时追求：

~~~text
低延迟
高流畅度
高数据完整度
低资源占用
~~~

这些目标会互相冲突，因此控制器不是把某个指标做到最大，而是在多重约束下维持稳定。

### 项目示例：QHZHC

QHZHC 的自动模式先尝试提高浏览器本地消费能力；如果持续积压而且单帧提交已经接近安全边界，才进一步降低上游输入量。

这个顺序体现了通用设计思想：

~~~text
先利用本地剩余能力
        ↓
本地能力达到边界
        ↓
再向上游反馈降载
~~~

这样可以尽量保留数据密度，而不是一出现积压就直接减少数据。

### 答辩关注点

如果被问“为什么不固定一个经验参数”，可以回答：不同设备、地图模式和历史规模的可承受负载不同，固定参数只能适用于局部场景，反馈控制可以根据真实运行结果动态修正。

## 八、过载判断必须同时考虑容量、延迟和趋势

仅看到“队列里有 20 条数据”不能说明系统已经过载，因为这可能只是瞬时突发。

判断持续过载至少需要三个维度。

### 【容量】

当前积压多少，用来描述缓冲压力。

### 【延迟】

最老的数据已经等待多久，用来描述实时性损失。

两个系统都可能有相同积压量，但一个最老数据只等待几十毫秒，另一个已经等待数秒，对用户体验的影响完全不同。

因此：

> 队列长度描述“多少”，数据年龄描述“多旧”。

### 【趋势】

当前窗口与上一窗口相比，积压是在增长还是下降。

持续增长说明当前消费能力仍然追不上输入；持续下降则可能只是短暂突发，不需要马上进入强降载。

此外还要同时观察单次处理成本。如果当前提交已经非常重，就不能因为积压增长而继续盲目扩大单次工作量。

### 项目示例：QHZHC

QHZHC 的自动调节同时观察待处理量、最老数据等待时间、队列变化趋势、实际 FPS 和页面提交成本。

因此它不是“队列超过某个数量就限流”的单阈值方案，而是综合判断：

~~~text
系统有没有持续落后
+
页面还有没有增加消费的空间
~~~

### 工程规范

过载检测应避免依赖一个瞬时样本。更稳妥的是结合连续观察窗口、变化趋势和尾部耗时，从而区分瞬时抖动与持续容量不足。

## 九、扩消费与限输入应该形成分级降载策略

系统过载时有两个基本方向：

~~~text
让消费者更快
或
让生产者更慢
~~~

工程上通常应该先尝试提高本地消费效率，例如：

- 合并提交；
- 使用增量更新；
- 减少重复状态更新；
- 把可并行纯计算移出主线程；
- 在安全范围内提高每次处理量。

这类优化尽量不牺牲数据完整度。

只有当本地已经达到安全上限，继续增加单次工作只会造成长帧时，才应该向上游反馈降载。

常见输入降载方式包括：

- 限制频率；
- 降采样；
- 合并重复状态；
- 只保留最新状态；
- 丢弃低优先级数据；
- 使用更低精度订阅。

### 项目示例：QHZHC

QHZHC 优先调整本地消费能力，只有持续过载且页面提交成本已经达到安全边界时，才降低实时输入档位。

这个顺序说明：数据完整度本身也是系统目标，性能优化不能简单等同于“少发一点数据”。

### 答辩关注点

如果被问“为什么检测到掉帧后不立即降低服务端发送量”，应说明：掉帧可能只是瞬时波动或本地批处理效率不足，需要先确认本地是否仍有安全余量；只有持续过载才需要牺牲输入密度。

## 十、稳定的自动控制需要滞回、连续窗口和冷却时间

如果控制器只根据一个采样窗口做决策，很容易形成 Oscillation（震荡）：

~~~text
当前过载
→ 降低输入

下一窗口恢复
→ 立即提高输入

随后再次过载
→ 再次降低输入
~~~

为了稳定控制过程，通常需要三类机制。

### 【连续窗口】

只有连续多个窗口都显示过载，才进入更强的降载策略。这样可以过滤一次 GC、一次复杂交互或一次网络突发。

### 【Hysteresis（滞回）】

进入过载和退出过载使用不同条件。例如进入降载可以相对敏感，而恢复需要持续健康更长时间。

### 【Cooldown（冷却时间）】

一次重要调节后，短时间内禁止再次切换输入档位，让系统有时间体现上一次调整的真实效果。

### 项目示例：QHZHC

QHZHC 的自动控制不会每次采样都立即切换输入档位，而是使用连续过载窗口、持续健康窗口和冷却时间。

这对应一个通用稳定性原则：

> 降载可以较快，恢复应该更谨慎。

### 答辩关注点

如果被问“自动模式如何避免参数一直上下波动”，不能只说“加了阈值”，还要说明连续窗口、滞回和冷却三者分别解决什么问题。
---

## 十一、性能指标必须按问题分层，不能用一个 FPS 解释全部性能

实时性能分析最常见的误区，是试图用一个指标解释所有问题。

例如：

~~~text
FPS 高
≠
数据一定没有积压

FPS 低
≠
一定是输入数据太多
~~~

不同指标回答的是不同问题：

| 指标类型 | 回答的问题 |
| --- | --- |
| 输入速率 | 上游送进来多快 |
| 消费速率 | 下游处理多快 |
| 队列长度 | 当前积压多少 |
| 数据年龄 | 实时显示落后多久 |
| 提交频率 | 页面多久触发一次业务更新 |
| 提交耗时分位数 | 单次业务提交有多重 |
| FPS | 浏览器整体帧调度能力如何 |
| Long Animation Frame | 是否出现明显长帧，以及长帧里发生了什么 |

### P95 比平均值更适合观察尾部成本

如果绝大多数提交很快，但少量提交明显很慢，平均值会把这些卡顿摊薄。

因此工程上常用 P95、P99 等分位数观察尾部成本。

但仍要注意：业务提交耗时不等于浏览器完整一帧耗时。它只描述被测量的那一段业务路径。

### LoAF 用于长帧归因

Long Animation Frame（长动画帧，LoAF）可以记录超过 50 ms 的长渲染帧，并提供脚本、渲染起点和样式布局等信息。

官方资料：

- MDN Long Animation Frames：https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing

### 项目示例：QHZHC

QHZHC 同时区分真实 rAF 帧率、页面业务提交频率、页面提交耗时、待处理队列和 LoAF。

这可以帮助区分：

~~~text
队列越来越长
→ 优先检查吞吐

队列为空但 FPS 下降
→ 优先检查单次渲染复杂度和长帧

提交频率下降但 FPS 上升
→ 可能是批处理减少了固定提交成本
~~~

### 工程规范

每个性能指标都应该明确：定义、采样位置、统计窗口、单位、代表什么、不代表什么。指标命名模糊会直接导致错误归因。

---

## 十二、吞吐稳定与渲染复杂度稳定是两个不同问题

一个实时系统可能满足：

~~~text
输入速率 ≈ 消费速率
队列长期为空
~~~

但页面仍然越来越卡。

原因是单次消费成本可能随着历史状态增长。

例如地图轨迹持续累积时，如果每新增一个点都需要重新扫描、重算或更新大量历史对象，那么单次更新复杂度会随着历史规模上升。

因此实时页面性能至少要分成两个正交问题：

~~~text
吞吐问题
→ 每秒需要处理多少数据

复杂度问题
→ 每次处理一批数据需要多少成本
~~~

背压、队列和批处理主要解决吞吐问题。

增量渲染、对象复用、历史窗口、空间索引、聚合和降采样主要解决复杂度问题。

### 项目示例：QHZHC

QHZHC 在调高批处理能力后，可以缓解待处理数据积压；但历史地图轨迹持续增长时，FPS 仍可能逐步下降。

这说明：

> 队列被清空，只能证明消费吞吐追上了输入，不能证明地图更新复杂度保持稳定。

因此地图性能还需要继续研究历史轨迹是否全量重算、地图对象是否持续增长、是否能够增量追加，以及是否需要可视窗口和降采样。

### 答辩关注点

如果被问“队列没有积压了为什么还掉帧”，应回答：吞吐稳定与单次更新复杂度稳定不是一回事，历史对象增长后单次提交可能越来越重。

---

## 十三、Web Worker 解决计算隔离，但不能替代主线程渲染

Web Worker（Web 工作线程）适合把不依赖 DOM 的纯计算从主线程移走。

典型适合任务包括：

- 数据解析；
- 数据清洗；
- 聚合计算；
- 批量坐标转换；
- 数学计算；
- 无 DOM 依赖的预处理。

但很多工作仍然必须在主线程完成，例如：

- DOM 更新；
- Vue 组件状态提交；
- 用户事件；
- 页面生命周期；
- 与地图和图表实例的最终协调。

因此 Worker 的正确使用原则不是“掉帧就上 Worker”，而是：

> 先通过性能分析找到可迁移的纯计算，再把这部分计算移走。

### 项目示例：QHZHC

如果 QHZHC 的坐标转换、数据聚合或复杂解析成为明显长任务，可以考虑迁移到 Worker。

但如果主要耗时来自地图实体更新、Vue 更新或图表重绘，仅把 WebSocket 接收搬到 Worker 并不会让真正的渲染成本消失。

这个例子说明性能优化必须遵循：

~~~text
先归因
再选工具
~~~

### 答辩关注点

如果被问“为什么不直接用 Worker 解决卡顿”，应说明 Worker 只能减轻可并行计算，不能替代主线程 UI 渲染；是否值得使用必须由 profiling、LoAF 或 Performance Timeline 的归因结果决定。

---

## 十四、实时系统的降级策略必须服从数据语义

当系统容量不足时，“少处理一些数据”并不是完整方案。

首先要判断数据属于什么语义。

### 【状态型数据】

例如当前温度、当前价格、当前坐标。

中间状态往往可以合并，只保留较新的状态。

### 【事件型数据】

例如告警、支付、点击、异常事件。

每条记录都可能具有独立业务意义，通常不能随意丢弃。

### 【连续轨迹型数据】

例如 GPS 轨迹和传感器曲线。

可以考虑：

- 均匀降采样；
- 形状保真抽稀；
- 时间窗口；
- 不同缩放级别使用不同精度。

因此降级设计的原则是：

> 先理解数据语义，再决定合并、抽样还是完整保留。

### 项目示例：QHZHC

QHZHC 的走航轨迹属于连续采样数据。压力过大时可以降低单位时间进入浏览器的点数，但采样规则需要稳定，否则实时播放与历史重放可能表现出不同轨迹。

这个实践说明：性能降级不能只从前端视角考虑，还要保证业务语义和回放一致性。

### 工程规范

任何丢弃、合并或降采样策略都应明确：是否影响统计、是否影响重放、客户端与服务端是否需要一致、用户是否需要知道当前已经降级。

---

## 十五、自动控制优先选择可解释、可测试、可回退的策略

并不是所有自动调节都需要复杂算法。

一个工程可用的控制器首先应该：

~~~text
能解释
能复现
能测试
能回退
~~~

规则型反馈控制通常由这些元素组成：

~~~text
阈值
+
趋势
+
连续窗口
+
安全预算
+
冷却时间
~~~

这种策略的优点是：

- 每次决策有明确原因；
- 可以编写确定性单元测试；
- 出问题容易定位；
- 参数可以通过实验调整；
- 可以保留手动模式。

代价是：

- 阈值依赖场景；
- 对突发变化有一定响应延迟；
- 参数之间可能耦合；
- 不是数学意义上的全局最优。

### 项目示例：QHZHC

QHZHC 的自动渲染采用规则型反馈控制，并保留手动调节能力和决策原因。

因此答辩时可以清楚解释：为什么扩大本地批量、为什么停止继续扩大、为什么降低输入、为什么恢复。

比起把它描述成复杂“智能算法”，这种可解释设计更符合真实工程。

### 工程规范

自动策略最好同时具备：

- 手动模式；
- 参数上下限；
- 决策原因；
- 当前状态可视化；
- 快速关闭自动策略的能力。

这些属于 Operability（可运维性）和 Debuggability（可调试性）。

---

## 十六、可观测性不是附加功能，而是控制系统的一部分

自适应控制如果没有可观测性，就无法回答两个关键问题：

~~~text
控制器为什么做出这个决策
以及
这个决策到底有没有改善体验
~~~

因此至少要观测四类数据。

### 【输入侧】

- 接收速率；
- 实际订阅速率；
- 网络发送缓冲。

### 【队列侧】

- 当前积压；
- 最老数据等待时间；
- 队列变化趋势。

### 【渲染侧】

- FPS；
- 提交耗时分位数；
- LoAF；
- 地图或图表对象规模。

### 【控制侧】

- 当前调度级别；
- 触发原因；
- 最近一次调整时间；
- 是否处于降级状态。

### 项目示例：QHZHC

QHZHC 已经在页面侧记录一部分实时调度指标，同时接入 browser-monitor 作为统一前端监控 SDK。

如果进一步把这些控制指标纳入监控平台，就可以从单机调试升级到真实用户环境分析，例如按设备、版本和地图模式观察 FPS 分布、LoAF、队列延迟和自动降载触发率。

这体现了一个重要工程思想：

> 控制系统必须能够观测自身，否则只能“自动变化”，却无法证明为什么变化以及变化是否有效。

---

## 十七、工程验证需要可重复实验，而不是一次演示

实时性能非常容易受到机器、浏览器和当前系统负载影响。

因此“我试了一下感觉更流畅”不是充分证据。

一个可重复实验至少要固定：

~~~text
输入速率
历史数据规模
地图模式
浏览器版本
设备
测试时长
~~~

然后只改变一个因素，例如：

~~~text
逐条提交 vs 批处理
固定调度 vs 自适应调度
不限输入 vs 分级降载
~~~

建议同时观察：

- FPS P5 / P50；
- LoAF 数量和尾部分布；
- 队列峰值；
- 最大数据等待时间；
- 页面提交 P95；
- 内存趋势；
- 是否触发降载。

### 项目示例：QHZHC

QHZHC 已经有帧队列、自适应控制和实时客户端相关单元测试。项目答辩中还可以固定模拟器输入和历史数据规模，对比固定策略与自适应策略。

这样可以把：

~~~text
感觉更流畅
~~~

升级成：

~~~text
在相同负载下
积压峰值下降多少
数据延迟是否降低
长帧发生率是否变化
是否以降低数据密度为代价
~~~

### 答辩关注点

完整证据链应该是：

~~~text
问题现象
        ↓
指标定位
        ↓
设计方案
        ↓
代码实现
        ↓
自动化测试
        ↓
固定场景实验
        ↓
结果与能力边界
~~~

这比只展示一段优化代码更能证明工程能力。

---

## 十八、这一知识点最终要形成一套可迁移的设计框架

实时前端中的背压与自适应调度可以收束成下面的知识树：

~~~text
实时渲染系统
│
├─ 生产消费模型
│   ├─ 输入
│   ├─ 消费
│   └─ 积压
│
├─ 多层背压
│   ├─ 传输层
│   ├─ 应用缓冲层
│   └─ 渲染层
│
├─ 调度
│   ├─ 接收与渲染解耦
│   ├─ rAF
│   ├─ 时间切片
│   └─ 批处理
│
├─ 反馈控制
│   ├─ 过载检测
│   ├─ 扩消费
│   ├─ 限输入
│   ├─ 滞回
│   └─ 冷却
│
├─ 性能度量
│   ├─ 吞吐
│   ├─ 队列延迟
│   ├─ FPS
│   ├─ P95
│   └─ LoAF
│
├─ 数据语义
│   ├─ 状态型
│   ├─ 事件型
│   └─ 连续轨迹型
│
├─ 能力边界
│   ├─ rAF 不保证高 FPS
│   ├─ 批量不能无限增大
│   ├─ 背压不能解决历史渲染复杂度
│   └─ Worker 不能替代 UI 渲染
│
└─ 工程保障
    ├─ 可观测
    ├─ 可解释
    ├─ 可测试
    ├─ 可回退
    └─ 可重复验证
~~~

这套框架可以迁移到实时图表、监控大盘、地图轨迹、行情系统、协同编辑等场景。QHZHC 的作用是提供一个真实工程实例，让这些通用原则能够被具体观察、实现和验证。
